# 工作流子流程节点（SUB_PROCESS）· 前后端接口设计

> 关联文档：《审批流程配置接口设计.md》（流程定义/版本快照/发布校验）、《工作流提交与审批操作接口设计.md》（运行态四表/引擎语义/审批动作）。
> 本文是在既有审批流体系上新增节点类型 **SUB_PROCESS（子流程）** 的扩展设计：设计器可"点击进入子流程继续流程设计"，运行态父流程推进到子流程节点时启动**子流程实例**独立流转、结束后回推父流程。
> 章节结构沿用《用户注册与登录功能.md》模板。设计日期：2026-10-22。

---

## 1. 现状分析

### 1.1 既有节点类型与设计结构

- 前端 `types/workflow.ts` 现有 7 种节点类型：`START / APPROVER / CONDITIONS / CONDITION / PARALLEL / PARALLEL_BRANCH / TRANSACT`；流程文档 `WorkflowDoc = { name, updatedAt, root }`，节点 `WorkflowNode = { id, name, type, props, childNode, conditionNodes? }` 递归组织（主干 `childNode` 串联、分支 `conditionNodes` 横向展开）。
- 设计 JSON 整体存 `flow_process.draft_json`（草稿区），发布时冻结为 `flow_process_version.design_json` 不可变快照；服务端不逐节点建 Java 模型（Jackson `JsonNode` 遍历）。
- 设计器组件族：`WorkflowCanvas / NodeChain / NodeCard / AddNodeButton / NodePropDrawer / WorkflowToolbar`，状态集中于 `stores/workflow.ts`；发布校验由前端 `useWorkflowValidate` 与后端发布接口最小结构校验（《审批流程配置接口设计》§7.4）双侧对齐。

### 1.2 既有运行态机制（本文扩展的基础）

- 四表：`flow_instance / flow_task / flow_task_log / flow_cc`；实例引用 `process_version_id` 读版本快照流转，草稿编辑/再发布不影响在途实例。
- 引擎四件套（`FlowEngine / EngineCtx / FlowEngineSupport / FlowEngineImpl / FlowApproverResolver`）：`advance` 沿 `childNode` 递归推进，条件/并行容器用内存回溯法（`FlowDesignCursor`）定位与汇合，天然支持容器任意嵌套。
- 并发：实例级推进锁 `approval:instance:advance:{instanceId}` + 发起锁；"同一单据仅一个进行中实例"由发起锁内 count RUNNING 兜底。
- 审批记录口径（2026-10-19 起）：**每次操作仅一条 `flow_task_log`**，系统说明经 `stageActionLog + addEngineNote + flushActionLog` 聚合落库。

### 1.3 痛点（为什么需要子流程）

1. 复杂流程只能平铺在一张画布上，节点多、层级深，可读性差；
2. 可复用的审批段落（如"法务审查"）无法作为整体封装、单独设计；
3. 子段落无独立的时间线/待办上下文，跨段落排查审批记录困难。

### 1.4 术语与实体关系

| 术语 | 含义 |
|---|---|
| 父流程 / 父实例 | 包含 `SUB_PROCESS` 节点的设计及其发起的实例（根实例或上层子实例，相对概念） |
| 子流程 / 子实例 | `SUB_PROCESS` 节点内嵌的子设计（`subDoc`）/ 该节点运行时创建的流程实例（`parent_instance_id` 指向父实例） |
| 流程树 | 根实例 + 其全部子孙实例（`root_instance_id` 相同），推进锁与级联操作以树为单位 |
| 深度 depth | 嵌套层数：根实例 =0，其直接子实例 =1，依此类推（上限见 §10 `max-depth`） |

## 2. 目标与范围

### 2.1 本期（V1）

1. **新节点类型 `SUB_PROCESS`（子流程）**：节点属性**内嵌**完整子设计 `props.subDoc`（结构与 `WorkflowDoc` 一致，root 为 `START`）；随父设计一起保存草稿、发布快照，**无独立流程定义**。
2. **设计器钻入编辑**：点击子流程节点卡片进入子流程设计视图（面包屑"主流程 / 子流程名 / …"）。**子流程设计视图与现有流程设计页面完全同构**——同一个设计页面内切换视图（`stores/workflow.ts` 设计视图栈，非新开独立路由），复用整套画布组件（`WorkflowCanvas / NodeChain / NodeCard / AddNodeButton / NodePropDrawer / WorkflowToolbar`）与既有交互：同样的添加节点菜单、同样的节点属性抽屉、同样的画布滚动/连线/校验标红。子流程视图内仍可添加审批/条件/并行/办理/子流程节点，支持嵌套（深度 ≤3）。
3. **发布校验增强**：对 `subDoc` **递归**执行既有全部最小结构校验规则 + 深度上限 + 摆放位置限制（§4.2）。
4. **运行态子实例流转（两种推进模式 `advanceMode`，节点级可配）**：父流程推进到 `SUB_PROCESS` 节点 → 引擎**自动**创建子流程实例并推进其首个审批节点。此后父流程行为由模式决定：
   - **`WAIT`（等待，默认）**：父实例在节点处等待；子实例主干链走完 → 子实例 `COMPLETED` 并回推父流程 `SUB_PROCESS.childNode`；子实例被拒绝（终止语义）→ 父流程树整体 `REJECTED`；
   - **`IMMEDIATE`（启动即继续）**：子实例启动后父流程**立即**继续推进 `SUB_PROCESS.childNode`（旁路子流程，不阻塞）；子实例随后自行流转至终态，完成**不回推**父流程、拒绝终止**不向上传播**（父流程不受影响）。
5. **列表与详情适配**：待办/已办正常展示子流程任务并标注"子流程"徽标；"我发起的"与单据审批状态仅按**根实例**口径；实例详情返回子实例摘要卡片，可逐级进入查看子实例时间线。

### 2.2 明确不做（避免过度设计）

| 项 | 决策 | 理由 |
|---|---|---|
| 引用式子流程（节点引用另一个 `flow_process` 定义，跨流程复用） | 不做，V2 | 引用式需固定引用子定义某版本、跨流程发布递归校验与引用关系表，复杂度高；内嵌式值拷贝随父快照天然不可变、零同步问题。有真实复用诉求再引入 |
| 子流程独立发起 | 不做 | 子流程不是 `flow_process`，不出现在"可发起流程"列表，仅由父流程运行时触发 |
| 跨子流程边界退回（父上游节点 ↔ 子流程内部节点） | 不做 | 退回目标集合（`getRejectTargets`）仍限定"当前 doc 内的 START/APPROVER"；跨实例回退破坏子实例状态机一致性 |
| 子实例单独撤销 / 单独重新发起 | 不做 | 撤销必须从根实例发起、树级联取消（§4.3）；单据重新发起走既有根实例链路 |
| 分支容器（CONDITIONS/PARALLEL）分支列内的 SUB_PROCESS | **发布校验拦截**（40067） | 并行汇合"分支链无 PENDING 任务"判定需扩展感知"子实例未完成"，回溯算法复杂化；V1 限定子流程仅可摆在**主干链**（含子 doc 内主干），分段诉求用"子流程内放容器"表达（§13） |
| 子流程变量映射 / 父子传参 | 不做 | 子实例与父实例共享同一 `form_snapshot`（同一单据），条件求值天然一致 |
| 子流程失败策略（子拒绝后父流程走其他分支） | 不做（`advanceMode=IMMEDIATE` 已覆盖"子失败不影响父"诉求） | WAIT 子拒绝 → 父终止（§4.4.3）；IMMEDIATE 子拒绝 → 父不受影响；"拒绝后按分支路由"仍不做，V2 可扩展 `failedPolicy` |
| 子流程超时/催办、消息通知 | 不做 | 随 V2 定时任务体系与通知域 |

## 3. 技术选型

| 能力 | 选型 | 说明 |
|---|---|---|
| 子设计存储 | **内嵌 `props.subDoc`**（完整 `WorkflowDoc` 结构） | 随父 `design_json` 一起保存/发布/快照；前后端零转换契约延伸；发布快照不可变语义天然覆盖子流程；不新增配置域表与接口 |
| 子实例存储 | **`flow_instance` 同表加列**（`parent_instance_id / parent_node_id / root_instance_id / depth / design_json`） | 复用实例/任务/日志/抄送全链路与引擎；子实例 `design_json` 冗余存 `subDoc`（= 父版本快照发布时内容），引擎 `loadDesign` 统一口径：根实例读版本表、子实例读自身冗余列 |
| 子实例身份 | `process_id/code/version/version_id/biz_*/form_snapshot/start_user_*` 全部**继承父实例**；`process_name` 冗余为 `{父流程名}·{子流程节点名}` | 同一单据、同一发起人（`INITIATOR` 穿透解析）、同一版本快照；`process_name` 拼接后列表直显子流程上下文，免 join |
| 推进模式 | 节点属性 `advanceMode: WAIT/IMMEDIATE`（缺省 `WAIT`），子实例行冗余 `advance_mode` 列 | `WAIT`=等待子流程完成再走下一节点；`IMMEDIATE`=子流程启动后直接走下一节点（旁路异步语义）；子实例侧回推/终止传播判定读自身列，避免每次回溯父快照定位节点 props |
| 推进锁 | **树级锁**：`approval:instance:advance:{rootInstanceId}` | 父锁内建子实例需推进子、子锁内回推需父锁，按实例分锁会构成锁环死锁；树级单锁彻底规避（§4.4.5）；`IMMEDIATE` 下父与子并行流转，也由树级锁统一串行化 |
| DDL 脚本 | `backend/sql/06-sub-process-schema.sql` | `ALTER TABLE flow_instance` 增列 + 存量回填（§4.1）；02~05 编号已占用 |
| 深度限制 | 后端配置 `approval.sub-process.max-depth`（默认 3）+ 前端同名常量 | 前端入口级拦截（隐藏添加入口），后端发布校验兜底 |

## 4. 数据模型设计

### 4.0 总览：全部复用既有表，不新建任何表

子流程扩展**不新增任何表**（无"子流程定义表"、无"子流程实例表"），各表改动情况如下：

| 表 | 来源脚本 | 改动 |
|---|---|---|
| `flow_process`（流程定义） | 既有（03） | **零改动**——`subDoc` 内嵌于 `draft_json`/快照 `design_json` 随主文档存取 |
| `flow_process_version`（版本快照） | 既有（03） | **零改动**——发布时 `subDoc` 随父 `design_json` 一起冻结进快照 |
| `flow_instance`（流程实例） | 既有（05） | **唯一有改动的表**：增 6 列 + 2 索引（§4.1，新脚本 06）；子实例即 `parent_instance_id` 非空的一行，`parent_instance_id IS NULL` 即根实例 |
| `flow_task / flow_task_log / flow_cc` | 既有（05） | **零改动**——子实例的任务/审批记录/抄送与根实例完全同构，照常落这三张表 |

说明：§4.2 不是新表，是 `design_json` 里 `SUB_PROCESS` 节点**内嵌的 JSON 结构契约**。全部复用的前提是 §3 的两个选型——**内嵌式**子设计（随父快照走，不落定义表）与**子实例同表加列**（复用四表全链路，避免任务/日志/抄送双轨维护）。

### 4.1 表：`flow_instance` 增列（脚本 `06-sub-process-schema.sql`）

```sql
-- 子流程节点扩展：实例表增列 + 存量回填（一次性执行）
ALTER TABLE flow_instance
    ADD COLUMN parent_instance_id BIGINT      DEFAULT NULL COMMENT '父实例 ID(子流程实例指向父实例；根实例为 NULL)' AFTER biz_title,
    ADD COLUMN parent_node_id     VARCHAR(64) DEFAULT NULL COMMENT '父流程中的子流程节点 ID(SUB_PROCESS 节点 id)' AFTER parent_instance_id,
    ADD COLUMN root_instance_id   BIGINT      NOT NULL DEFAULT 0 COMMENT '流程树根实例 ID(根实例=自身；树级推进锁/级联按此)' AFTER parent_node_id,
    ADD COLUMN depth              TINYINT     NOT NULL DEFAULT 0 COMMENT '嵌套深度(根实例=0)' AFTER root_instance_id,
    ADD COLUMN design_json        LONGTEXT    DEFAULT NULL COMMENT '子流程设计快照(子实例=父版本快照内 SUB_PROCESS 节点的 subDoc；根实例为 NULL 读版本表)' AFTER depth,
    ADD COLUMN advance_mode       VARCHAR(16) DEFAULT NULL COMMENT '推进模式(子实例冗余创建时的节点 advanceMode：WAIT=父等待完成/IMMEDIATE=父启动即继续；根实例为 NULL)' AFTER design_json,
    ADD KEY idx_parent (parent_instance_id),
    ADD KEY idx_root (root_instance_id, status);

-- 存量数据回填：既有实例均为根实例
UPDATE flow_instance SET root_instance_id = id WHERE root_instance_id = 0;
```

取舍：

- **不拆独立子实例表**：子实例的任务生成、完成判定、日志、抄送、列表、可见性与根实例完全同构，拆表需全链路双轨；同表 + `parent_instance_id IS NULL` 过滤即可区分。
- **`design_json` 冗余于子实例行**：引擎对"实例 → 设计快照"的读取收敛单口径（§4.4.6），子实例流转无需每次回溯父快照定位 `subDoc`；冗余值发布即冻结，不破坏版本快照不可变语义。
- **`root_instance_id NOT NULL DEFAULT 0` 再回填**：避免可空列参与索引与判定；上线窗口执行脚本，无新旧锁 key 并存期（§13）。
- **`idx_root(root_instance_id, status)`**：树级联取消、树状态汇总单索引覆盖。
- **`advance_mode` 冗余于子实例行**：子实例侧"完成是否回推、拒绝是否向上传播"两个分叉判定读自身列即可，无需回父快照定位 `parent_node_id` 节点的 props（父可能已终态/父版本快照递归回溯成本高）；根实例恒为 NULL，旧数据无感。

### 4.2 `SUB_PROCESS` 节点契约（`design_json` 内嵌结构）

前端类型扩展（`types/workflow.ts`）：

```ts
export enum NodeType {
  // ...既有 7 种
  SUB_PROCESS = 'SUB_PROCESS',
}

/** 子流程节点属性：内嵌完整子设计，随父设计保存/发布/快照 */
export interface SubProcessProps {
  subDoc: WorkflowDoc   // 结构与主文档一致，root 固定为 START
  /** 推进模式：WAIT=父流程等待子流程完成后继续（默认）；IMMEDIATE=子流程启动后父流程立即继续下一节点（旁路，不等待） */
  advanceMode: 'WAIT' | 'IMMEDIATE'
}
```

结构示例（父主干 `a(APPROVER) → SUB_PROCESS(法务审查) → c(APPROVER)`）：

```json
{
  "id": "9f3c…", "name": "法务审查", "type": "SUB_PROCESS",
  "props": {
    "advanceMode": "WAIT",
    "subDoc": {
      "name": "法务审查子流程", "updatedAt": 1779000000000,
      "root": {
        "id": "s1…", "name": "发起人", "type": "START",
        "props": { "rangeType": "ALL", "memberIds": [], "roleIds": [] },
        "childNode": {
          "id": "s2…", "name": "法务初审", "type": "APPROVER",
          "props": { "source": "MEMBER", "memberIds": ["1001"], "roleIds": [], "leaderLevel": 1,
                     "multiMode": "AND", "emptyPolicy": "TO_ADMIN", "canRejectToStart": false,
                     "rejectTargetId": "", "buttons": [] },
          "childNode": null
        }
      }
    }
  },
  "childNode": { "id": "c…", "name": "总经理审批", "type": "APPROVER", "props": {}, "childNode": null }
}
```

契约要点：

- **`subDoc.root` 固定为 `START`**（与主文档一致，保证 `advance(subDoc.root.childNode)` 入口统一）；子 doc 内 `START` 的发起范围配置**无运行语义**（子流程由父流程自动触发），设计器在子流程视图中隐藏该配置并显示说明文案。
- **子 doc 内允许全部既有节点**（审批/条件/并行/办理），也允许再嵌 `SUB_PROCESS`（深度受 §10 限制）；**不允许**在 `CONDITIONS/PARALLEL` 的分支列（`conditionNodes`）内出现 `SUB_PROCESS`（发布校验 40067）。
- `WorkflowNode.id` 为 uuid，主/子 doc 全局唯一，子实例任务 `node_id` 无冲突；发布校验与运行引擎对 `subDoc` 递归复用同一套遍历逻辑。
- **`advanceMode` 推进模式（§4.4.1/§4.4.2/§4.4.3）**：取值仅 `WAIT`/`IMMEDIATE`，**缺省视为 `WAIT`**（旧快照无此字段自动兼容）；发布校验非法值 → 40065；子实例创建时将模式冗余写入 `flow_instance.advance_mode`；设计器子流程节点抽屉提供单选（默认 WAIT），卡片显示模式徽标（"等待子流程完成"/"启动即继续"）。

### 4.3 状态机与树级流转总览

实例/任务状态机**不变**（`RUNNING/COMPLETED/REJECTED/CANCELED`），新增**父子联动规则**：

```
父实例推进 ──advance──▶ SUB_PROCESS 节点（advanceMode）
                          │ 自动创建子实例(RUNNING, depth+1, advance_mode 冗余)
                          │ 并推进子 doc 首个审批节点
                          │
              ┌───────────┴────────────┐
        advanceMode=WAIT          advanceMode=IMMEDIATE
        父实例等待(无任务)           父实例立即 advance(SUB_PROCESS.childNode)
              ▼                          ▼
      子实例独立流转              子实例旁路独立流转(父不等待)
              │                          │
   ┌──────────┴───────────┐   ┌──────────┴───────────┐
   子实例主干链走完      子实例终止 REJECTED   子实例主干链走完    子实例终止 REJECTED
   子实例 COMPLETED      祖先链逐级 REJECTED  子实例 COMPLETED    仅自己(含下层子树)REJECTED
   回推父 advanceFrom    父树全部 PENDING      不回推(父早已走过)  不向上传播(父不受影响)
   (SUB_PROCESS.childNode) 级联 CANCELED
   
   （两种模式下：根实例 CANCEL/终止 → 仍按 root_instance_id 整树级联取消）
```

| 触发 | 树级行为（同一树级推进锁 + 同一事务内完成） |
|---|---|
| 父 `advance` 遇 `SUB_PROCESS`（WAIT） | 建子实例 → 子实例 START 日志 → 推进子 doc 首个审批节点 → 父实例等待；父实例触发记录聚合系统说明「进入子流程【节点名】，等待其完成」 |
| 父 `advance` 遇 `SUB_PROCESS`（IMMEDIATE） | 建子实例 → 子实例 START 日志 → 推进子 doc 首个审批节点 → **父实例立即继续** `advance(SUB_PROCESS.childNode)`；父实例触发记录聚合系统说明「进入子流程【节点名】，启动后继续」 |
| 子实例主干链尾（WAIT） | 子实例 `COMPLETED` + `finish_time` → 回父上下文 `advanceFrom(SUB_PROCESS.childNode)`；子实例最后一条操作记录聚合「子流程已完成，父流程继续」 |
| 子实例主干链尾（IMMEDIATE） | 子实例 `COMPLETED` + `finish_time`，**不回推父实例**（父未等待）；操作记录聚合「子流程已完成（旁路）」 |
| 子实例 REJECT 终止（WAIT） | 子实例 `REJECTED` → **逐级向上**：父实例 `REJECTED`、父全部 PENDING 任务（含并行分支、下层子实例树）级联 `CANCELED`；父若为子实例继续向上 |
| 子实例 REJECT 终止（IMMEDIATE） | 仅子实例自身（含其下层子树）`REJECTED`、PENDING 级联 `CANCELED`；**父流程不受影响**继续流转；操作记录聚合「子流程被拒绝（旁路，父流程不受影响）」 |
| 子实例 REJECT `rejectTargetId` / RETURN / 退回发起人 | **子实例内部**退回/重提，语义与根实例一致（原 §4.6.6 原样适用，作用域=子 doc）；不波及父（两种模式相同） |
| 根实例 CANCEL（撤销） | 根 `CANCELED` + 按 `root_instance_id` 级联取消树内全部非终态子实例及其 PENDING 任务（**WAIT/IMMEDIATE 均级联**） |
| 根实例其他节点 REJECT 终止 | 同上级联（树内子实例一并终止，含 IMMEDIATE） |

> 子实例不可被直接 CANCEL（`POST /api/approval/instance/{id}/cancel` 对 `parent_instance_id != null` 返回 40068）；子实例详情/任务办理等读操作与根实例无差别。

### 4.4 引擎语义（核心）

#### 4.4.1 推进进入子流程（`advance` 新增分支）

```
advance(ctx, node):
    node == null        → 链尾判定：
                          ctx 为子实例且位于子 doc 主干根链 → completeSubInstance(ctx)
                          否则 → 既有链尾逻辑（分支汇合判定 / 实例 COMPLETED）
                          // 注：IMMEDIATE 下父链尾照常判定父实例 COMPLETED，
                          //     不感知在途旁路子实例（§4.4.2）
    type == TRANSACT    → 记 AUTO_PASS，advance(node.childNode)          // 既有
    type == APPROVER    → 解析审批人；生成任务；停止                       // 既有
    type == CONDITIONS  → 求值选定分支 → advance(分支首节点)               // 既有
    type == PARALLEL    → 各分支列 advance；停止（等待汇合）               // 既有
    type == START       → advance(node.childNode)                         // 既有
    type == SUB_PROCESS → buildSubInstance(ctx, node)                    // 新增：建子实例并推进其首节点
                          advanceMode == WAIT      → 停止（父实例等待子实例完成）
                          advanceMode == IMMEDIATE → advance(ctx, node.childNode)（父立即继续）
```

`buildSubInstance(ctx, node)`（同一树锁 + 事务内）：

1. 落子实例行：身份字段继承父实例（§3），`parent_instance_id=ctx.instanceId`、`parent_node_id=node.id`、`root_instance_id=ctx.rootInstanceId`、`depth=ctx.depth+1`、`design_json=node.props.subDoc 序列化`、`advance_mode=node.props.advanceMode（缺省 WAIT）`、`status=RUNNING`；
2. 子实例 START 日志（`instance_id=子实例`）+ 父实例侧 `addEngineNote`「进入子流程【{节点名}】{WAIT：等待其完成 | IMMEDIATE：启动后继续}」聚合进本次触发操作记录；
3. 以子上下文 `subCtx = EngineCtx(子实例, loadDesign(子实例), …)` 执行 `advance(subCtx, subDoc.root.childNode)`（空审批人策略、条件求值、降级等既有语义原样作用于子 doc）；
4. 返回父上下文后按模式分叉（伪代码 SUB_PROCESS 行）：`WAIT` 停止等待，`IMMEDIATE` 继续 `advance(ctx, node.childNode)`——同一锁同一事务内连续完成，父与旁路子实例的后续流转均由树级锁串行化，无并发窗口。

> `SUB_PROCESS` 无任务、无按钮、无审批人解析（类似 TRANSACT 的直通定位，但内部承载完整流程）；WAIT 模式下父实例在节点处无 PENDING 任务，天然处于"等待子实例"状态；IMMEDIATE 模式下该节点对父流程等价于"触发即直通"。

#### 4.4.2 子实例完成回推（`completeSubInstance`，按 `advance_mode` 分叉）

1. 子实例 `status=COMPLETED`、写 `finish_time`；
2. 子实例侧 `addEngineNote` 聚合进**触发本次链尾的最后一条操作记录**（维持"每次操作仅一条 log"口径，不单独落 ENGINE 记录）：
   - WAIT 子实例：「子流程已完成，父流程继续」；
   - IMMEDIATE 子实例：「子流程已完成（旁路）」，**不回推、无父侧动作**（父未等待，可能仍在后续节点流转或已终态），流程结束；
3. **仅 WAIT 子实例**回父上下文：以父实例 + `loadDesign(父)` 构造 `parentCtx`，定位父快照中 `parent_node_id` 节点，`advanceFrom(parentCtx, SUB_PROCESS.childNode)`——父后续若是 `MANUAL` 路由容器等既有语义照常（此时无人在 PASS 选路 → 按既有降级规则自动处理并记系统说明）。

> **父实例完成判定不感知 IMMEDIATE 子实例**：父主干链尾（或并行汇合完成）即父 `COMPLETED`，不等待在途旁路子实例——`WAIT` 子实例不可能晚于父链尾（父后继仅在子实例完成后推进），故父链尾时在途子实例必然全部为 IMMEDIATE，判定天然正确。父（根实例）`COMPLETED` 后 IMMEDIATE 子实例继续独立流转至终态（树级锁与级联取消仍生效），单据状态（§9 `biz-status`）以根实例为准，属预期语义。

#### 4.4.3 终止/撤销的树级联

- **统一封装 `cascadeTreeTerminal(rootInstanceId, targetStatus, 触发记录)**：按 `idx_root` 查树内全部非终态子实例逐个置 `REJECTED`/`CANCELED`（`finish_time`），各实例 PENDING 任务级联 `CANCELED`（含加签链、替身任务）——**不区分 WAIT/IMMEDIATE，整树全部级联**。
- **子实例终止向上传播（仅 WAIT 子实例）**：子实例 REJECT 走终止语义时，沿 `parent_instance_id` 链向上：每层父实例置 `REJECTED` 并清理其全部 PENDING 任务（父内并行列、更上层子树一并取消），直到根实例；触发记录（子实例内该次 REJECT）聚合「子流程被拒绝，父流程已终止」。
- **IMMEDIATE 子实例终止不向上传播**：仅自身（含其下层子树）`REJECTED`、PENDING 级联 `CANCELED`，父流程及其余旁路子实例不受影响，继续流转；触发记录聚合「子流程被拒绝（旁路，父流程不受影响）」。
- **根实例 CANCEL / 其他节点 REJECT 终止**：调用 `cascadeTreeTerminal` 一次完成（对齐既有"全部 PENDING 级联 CANCELED"口径，范围从单实例扩展为流程树；IMMEDIATE 在途子实例一并取消）。

#### 4.4.4 与既有特性的组合边界

| 特性 | 子流程下的行为 |
|---|---|
| 会签/或签/加签/转办/减签 | 任务链与判定逻辑不变（作用域=子实例任务集）；`INITIATOR` 来源解析为**根实例发起人**（穿透），子 doc 内"发起人确认"节点任务落在根发起人名下 |
| 条件求值 | 子实例共享父 `form_snapshot`（同一单据快照），`fieldKey` 取值口径不变 |
| 并行汇合 | 子 doc 内 PARALLEL 照常内存回溯；父 doc 分支列内禁入 SUB_PROCESS（§2.2），无跨实例汇合判定 |
| 人工路由/人工并行（MANUAL） | 上游 PASS 选路语义不变；若 SUB_PROCESS 完成回推后继为 MANUAL 且无人选路（非审批人直连），按既有降级规则自动路由并记系统说明 |
| 退回目标集合 | `getRejectTargets`/RETURN 目标仍收集"当前 doc 内的 START/APPROVER"；SUB_PROCESS 节点非 APPROVER 不入选；父流程退回到 SUB_PROCESS **之前**节点时，若子实例在跑则随 `cascadeTreeTerminal` 一并取消 |
| 驳回到发起人 / 重新提交（SUBMIT） | 作用域=子实例：刷新 `form_snapshot`（同一 Loader），子 doc 从首个审批节点重新推进；历史记录保留 |
| 空审批人/LEADER/SELF_SELECT 降级 | 既有降级与日志语义原样作用于子 doc 节点 |
| 父实例完成判定 / 单据状态 | 不感知 IMMEDIATE 子实例：父链尾即父 `COMPLETED`；`biz-status` 以根实例为准（§4.4.2） |
| 审批中禁编辑（40060） | 拦截口径仍为**根实例 RUNNING**；IMMEDIATE 子实例在跑不锁单据编辑（旁路语义，子实例评审的是发起时 `form_snapshot` 快照，单据后续修改不影响在途子实例） |
| next-approvers 预览穿透 | WAIT 模式照常穿透子 doc 取首审批节点；IMMEDIATE 模式子实例旁路启动，子 doc 首组审批人与父 `childNode` 首组审批人一并返回（两路并行推进） |

#### 4.4.5 锁策略调整（树级推进锁）

- 锁 key 由 `approval:instance:advance:{instanceId}` 改为 **`approval:instance:advance:{rootInstanceId}`**：`buildSubInstance`（父锁内推进子）与 `completeSubInstance`（子流转内回推父）不再交叉获取两级锁，规避"父→子、子→父"锁环死锁；整树串行化，审批频率低下可接受。
- `EngineCtx` 携带 `rootInstanceId/depth/parentInstanceId`，锁获取入口（Service 层任务动作/发起/撤销）统一按实例行解析根 ID 后加锁。
- 发起锁 `approval:instance:start:{bizType}:{bizId}` 不变；锁内"已有进行中实例"判定改**根实例口径**：`count(status=RUNNING AND parent_instance_id IS NULL AND biz_type=? AND biz_id=?)`——子实例 RUNNING 不阻塞单据重新发起（父树必已非 RUNNING 才可能重新发起）。

#### 4.4.6 设计快照读取（`loadDesign` 统一口径）

```
loadDesign(instance) = instance.designJson 非空（子实例）
                       ? parse(instance.designJson)          // subDoc 冻结副本
                       : parse(flow_process_version[instance.processVersionId].designJson)  // 既有
```

`FlowDesignCursor` 定位/回溯一律在"当前实例的设计 doc"内进行（根=版本快照、子=冗余 subDoc），节点 id 全局 uuid 唯一保证无歧义。

#### 4.4.7 预览接口穿透

- `next-approvers`（dryRun）：模拟推进遇 `SUB_PROCESS` → WAIT 节点递归进入 `subDoc.root.childNode` 继续模拟，返回穿透后的首个审批节点审批人（含多层嵌套）；IMMEDIATE 节点子实例旁路启动，子 doc 首组审批人与父 `childNode` 首组审批人一并返回（两路并行推进，与运行态真实路径一致，§4.4.1）；返回节点增 `scopeType`（`MAIN`/`SUB_PROCESS`）与 `scopeName`（主流程名/子流程节点名）标识归属，前端提交抽屉据此区分主/子流程并标注名称；
- `node-buttons`：`SUB_PROCESS` 非 APPROVER 节点，返回空按钮数组（既有行为天然覆盖）。

## 8. 安全设计要点

| 主题 | 设计 |
|---|---|
| 可见性扩展 | 子实例详情可见性 = **根实例参与人**（发起人 ∪ 根实例任务审批人 ∪ 抄送人）∪ **子实例自身参与人** ∪ ADMIN——父流程审批人可跟踪子流程进展；`InstanceDetailAssembler` 判定时向上并入根实例任务/抄送集（沿 `root_instance_id` 批量取） |
| 操作权限 | 子实例任务办理（PASS/REJECT/…）仍校验"操作人=assignee 且 PENDING"；树级流转在锁内同事务，无越权窗口 |
| 撤销约束 | 仅根实例发起人可撤销且整树级联；子实例直接撤销返回 40068，防"撤孩子留父亲"的半终止状态 |
| 深度防护 | 后端 `max-depth` 配置兜底 + 前端入口拦截，防构造超深嵌套 JSON 的恶意草稿（递归栈安全 ≤3 层） |
| 负载 | `subDoc` 随 `design_json` 存量增长，沿用 512KB 上限校验（§10 可配）；`design_json` 冗余仅子实例行，同单据总量可控 |
| 其余 | 沿用既有：逻辑删除过滤、`@PreAuthorize` 管理域（配置接口）、登录即可（运行态接口）、锁与事务防并发非法流转 |

## 9. API 设计（无新增 URL，既有接口行为增强）

统一约定不变（`ApiResponse<T>`、Long id 字符串化、时间 `yyyy-MM-dd HH:mm:ss`）。**配置域（/api/approval/process/\*）无任何新接口**——`subDoc` 内嵌于 `design_json`，保存/查询/发布走既有接口，仅发布校验增强。

| 接口 | 变化 |
|---|---|
| `POST /api/approval/instance/start` | 40049 判定改根实例口径（§4.4.5）；其余不变 |
| `POST /api/approval/instance/{id}/cancel` | `parent_instance_id != null` → 40068；根实例撤销整树级联 |
| `GET /api/approval/instance/mine`（我发起的） | 过滤 `parent_instance_id IS NULL`（子实例不单列） |
| `GET /api/approval/instance/{id}`（详情） | VO 增 `parentInstanceId/subProcessName/subInstances[]`；可见性扩展（§8）；时间线仍为本实例记录（子实例记录进子实例详情查看） |
| `GET /api/approval/instance/status`（单据状态批量） | 只统计根实例（子实例状态不外露为单据状态） |
| `GET /api/approval/task/todo` / `done` | 子实例任务正常出现，`TaskVO.subProcessName` 非空（实例名含"·子流程名"），前端加"子流程"徽标 |
| `GET /api/approval/task/{id}`（任务详情） | 增 `subProcessName`；其余（buttons/returnTargets/manualRouteOptions 等）按子 doc 节点语义原样返回；链后继为 SUB_PROCESS 且 IMMEDIATE 时增 `subProcessApproverOptions`（子流程首节点 + 父链下一节点，供 PASS 指定审批人） |
| `POST /api/approval/instance/next-approvers` | 遇 SUB_PROCESS 模拟推进：WAIT 穿透子 doc、IMMEDIATE 子 doc 首组审批人与父 childNode 首组审批人一并返回（§4.4.7） |
| `POST /api/approval/task/{id}/action`（PASS） | 下一节点为 SUB_PROCESS 且 IMMEDIATE 时，可携 `subProcessAssignees`（nodeId → userId）为主/子流程目标审批节点指定审批人（2026-10-23） |
| `POST /api/approval/instance/node-buttons` | SUB_PROCESS 节点返回空按钮数组（既有行为覆盖） |
| `GET /api/approval/instance/startable` | 不变（子流程无独立流程定义，天然不出现） |

## 11. 测试要点

**设计器（前端）**

- 添加子流程节点 → 卡片显示"子流程"与内部节点概要；点击钻入子视图、面包屑逐级返回；多级嵌套（3 层）与第 4 层入口隐藏；
- 子流程节点抽屉"推进方式"单选：WAIT（默认勾选"等待子流程完成后继续"）/ IMMEDIATE（"子流程启动后立即继续"），卡片徽标随选择切换；发布后 `design_json` 含 `advanceMode`，旧流程无该字段打开回显为 WAIT；
- 子视图内增删改节点、容器嵌套；`useWorkflowValidate` 递归报错并可定位（钻入对应视图可见标红节点）；
- 子视图 START 不显示发起范围；保存/发布提交的主文档包含完整 `subDoc`；旧流程（无子流程节点）打开/保存/发布零变化。

**发布校验（后端单测）**

- `subDoc` 缺失/根非 START → 40065；子 doc 内审批人空/条件无规则/人工路由 <2 列 → 40065（信息带「子流程【X】内：」前缀）；
- 深度 4 层 → 40066；分支列内 SUB_PROCESS（条件列/并行列/嵌套容器列）→ 40067；合法 3 层发布通过、快照含完整 subDoc。

**引擎（后端单测）**

- 父推进遇 SUB_PROCESS（WAIT）：子实例行字段（继承/冗余/depth/root/advance_mode）、START 日志、父侧聚合说明「进入子流程【X】，等待其完成」；
- 父推进遇 SUB_PROCESS（IMMEDIATE）：子实例启动 + **父立即继续** `childNode`（同一事务可见两段推进）；子 doc 内条件/并行/会签/空审批人降级/退回发起人重提等既有语义回归；
- WAIT 子实例正常走完 → COMPLETED + 回推父 `childNode`；IMMEDIATE 子实例走完 → COMPLETED **不回推**（父可能仍在跑或已终态）；IMMEDIATE 下父链尾 → 父 COMPLETED **不等待**在途旁路子实例；
- 子实例 REJECT 终止（WAIT）→ 祖先链全 REJECTED、并行分支任务与下层子树级联取消；REJECT 终止（IMMEDIATE）→ 仅自身 REJECTED、父继续流转不受影响；REJECT 带退回目标（两种模式）仅子实例内回退；
- 根撤销/终止 → 整树 CANCELED/REJECTED（**含 IMMEDIATE 在途子实例**）；直接撤销子实例 → 40068；
- 树级锁：父推进中并发办理子实例任务被串行化（含 IMMEDIATE 下父/子并行流转）；发起锁根口径（子实例 RUNNING 不阻止单据在父树结束后重新发起）；
- `loadDesign`：子实例读冗余列、根实例读版本表；父版本再发布不影响在途子实例；
- next-approvers：WAIT 穿透（含两层嵌套）；IMMEDIATE 子 doc 首组审批人与父 childNode 首组审批人一并返回。

**接口/页面（联调）**

- 待办/已办子流程任务徽标与实例名展示；"我发起的"无子实例；单据状态徽标按根实例；
- 详情页 subInstances 卡片逐级进入、子实例详情"返回父流程"；可见性：父审批人可看子实例、无关用户 40059。

## 13. 风险与取舍

| 风险/取舍 | 影响 | 应对 |
|---|---|---|
| 内嵌式不做跨流程复用 | 多流程引用同一段子流程须各自维护拷贝 | V1 无复用场景；V2 引入引用式（`flow_process` 关联 + 固定子定义版本），与内嵌式可并存 |
| 分支列内禁 SUB_PROCESS | "按条件进入不同子流程"须改为子流程内部再分条件 | 表达力换实现简单度（汇合判定零改动）；V2 扩展汇合判定感知子实例后放开 |
| 子拒绝即父终止（仅 WAIT；IMMEDIATE 子拒绝不向上传播） | WAIT 无"子失败父另路"策略；IMMEDIATE 下父通过后旁路子流程可能被拒，单据状态仍为已通过 | 前者 V2 扩展 `failedPolicy`；后者属 IMMEDIATE 旁路预期语义——详情 `subInstances` 卡片（含模式徽标）可跟踪旁路子流程终态，配置时以 WAIT 为默认引导 |
| IMMEDIATE 下父与旁路子实例并行流转 | 状态组合更复杂（父终态 + 子 RUNNING 等） | 树级推进锁统一串行化（无并发窗口）；完成/终止判定全部读子实例自身 `advance_mode` 分叉，无回溯歧义 |
| 树级锁粒度变粗 | 同树所有实例流转串行 | 审批频率低、临界区短（内存判定 + 少量写库）；换取零死锁设计 |
| `design_json` 冗余 | 子实例行存储增加（subDoc 全文） | 单实例量级 KB 级；换取 `loadDesign` 单口径与零回溯成本 |
| 发布校验/引擎递归深度 | 栈深随嵌套增长 | `max-depth=3` 硬上限双侧拦截 |
| 锁 key 切换（instanceId→rootInstanceId） | 上线窗口新旧 key 并存理论风险 | 脚本与代码同窗口发布（§4.1 一次性执行），不设兼容期 |
| 存量数据兼容 | 旧快照无 SUB_PROCESS 节点 | 引擎仅新增分支、既有路径零改动；`root_instance_id` 回填后行为与原先一致（回归项入 §11） |
| 审批记录分散于父/子实例 | 单页时间线看不到子流程明细 | 详情 `subInstances` 卡片逐级进入；V2 可做时间线聚合视图（按树合并渲染） |
