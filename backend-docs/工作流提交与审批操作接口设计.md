### 1.1 术语与实体关系

```
flow_process (1) ──< flow_process_version (1) ──< flow_instance (n)   # 实例引用发布版本快照（不可变）
flow_instance (1) ──< flow_task (n)      # 审批任务（会签时每个审批人一条）
flow_instance (1) ──< flow_task_log (n)  # 审批记录（每次操作一条，系统说明聚合进 detail）
flow_instance (1) ──< flow_cc (n)         # 抄送（待阅/已阅）
flow_instance (n) ──> biz (law_firm_select)   # biz_type + biz_id 逻辑挂接，通用化预留
flow_task (1) ──< flow_task (n)           # 加签/转办派生任务经 parent_task_id 成链
```

| 术语 | 说明 |
|---|---|
| 实例（instance） | 一次"提交审批"产生一条，绑定**发起时刻的已发布版本快照**，运行全程不受后续编辑/再发布影响 |
| 任务（task） | 实例推进到某 APPROVER 节点时按审批人解析结果生成的待办；会签模式下每个审批人各一条；加签/转办/委托派生新任务（`parent_task_id` 指向原任务） |
| 动作（action） | 审批人对任务的处理（PASS/REJECT/RETURN/TRANSFER/DELEGATE/ADD_SIGN/COMMENT/COPY）+ 发起人的 CANCEL |
| 抄送（cc） | 动作附带或发起时指定，产生待阅记录，不影响流转 |

## 2. 目标与范围

### 2.1 本期（V1）

1. **提交审批（发起）**：对律所选聘单据（`biz_type=LAW_FIRM_SELECT`）发起；通用的 `biz_type + biz_id` 模型为后续单据类型预留。校验流程已发布、发起范围（`initiator_type`/人员/角色）、单据存在且无进行中实例；发起时可选抄送人。
2. **引擎流转**：主干推进、条件分支求值（规则组 AND/OR、数值/字符串自适应）、并行分支（全分支完成汇合）、或签/会签、空审批人策略、驳回到指定节点/发起人、退回、撤销、重新提交。
3. **审批操作**：九种动作全量落地，统一入口 `POST /api/approval/task/{id}/action`（与前端 `ApprovalActionPayload` 一一对应）。
4. **列表**：待办/已办/我发起的/待阅/已阅五类分页列表 + 业务单据审批状态批量查询（供律所选聘列表徽标）。
5. **实例详情**：表单快照 + 审批记录时间线 + 当前用户视角操作面。
6. **下一节点审批人预览**：传流程 ID 与节点 ID 获取下一审批节点的审批人清单（节点 ID 缺省 = 发起后第一个审批节点），服务于发起前预览与办理时预览。
7. **节点动作按钮预览**：按流程 ID 与节点 ID 获取该节点配置的审批动作按钮清单（`enabled` 决定可用动作），服务于发起前/画布预览与操作栏渲染（任务未生成场景）。

### 2.2 明确不做（避免过度设计）

| 项 | 决策 | 理由 |
|---|---|---|
| LEADER 审批人来源、TO_LEADER 空审批人策略的真实主管链 | **运行时降级**（§4.6.5） | `sys_org` 无 leader 字段、`sys_user` 无汇报线，数据模型不支持；V2 引入主管模型后启用，降级有日志可审计 |
| SELF_SELECT 自选审批人（发起人人工指定） | **取消人工指定**，运行时降级（§4.6.5） | 分支路由**全自动**：需要"按单据内容动态路由审批人"的场景用**条件分支**表达——条件规则按英文 `fieldKey` 匹配表单快照，引擎自动判断走哪个分支节点，各分支下配置对应审批人，全程无人工选择交互 |
| DELEGATE 委托的"协助办理、仍算本人完成"语义 | 简化为**转办**语义，仅日志动作区分 | 双任务并存会破坏会签计数一致性；V1 用 parent_task_id 替换链表达 |
| 会签比例（如 2/3 通过）、一票否决配置 | 不做 | 仅 AND=全票通过 / OR=一票通过，与前端 `MultiApproverMode` 一致 |
| 消息通知（站内信/邮件/短信） | V2 | 需通知域基础设施，独立设计 |
| 催办、超时自动处理、审批委托规则（长期代理） | V2 | 需要定时任务与代理配置域 |
| 表单引擎/条件字段注册机制 | 不做 | `form_snapshot` 由业务域提供；条件字段 `fieldKey` 直接对应单据快照 JSON 字段名（`title/amount/reason`），前端条件规则配置输入即字段名 |
| 实例流程图的服务端反序列化建模 | 不做 | 沿用配置域策略：Jackson `JsonNode` 遍历快照 JSON，不建节点 Java 模型 |
| 审批中单据编辑 | **禁止**（40060） | 发起时冻结 `form_snapshot`，放行编辑会造成展示与求值不一致；`LawFirmSelectService` 更新/删除前校验无 RUNNING 实例 |
| 抄送范围/审批人组织可见性等高级数据权限 | 不做 | V1 可见性 = 参与人（发起人、任务审批人、抄送接收人）+ ADMIN |

## 3. 技术选型

| 能力 | 选型 | 放置 | 说明 |
|---|---|---|---|
| 持久层 | 四表 DO + `BaseMapper` | `ocr-dal` | `flow_instance`/`flow_task`/`flow_task_log`/`flow_cc`；无 join，分页后内存组装 VO |
| 快照引用 | 实例存 `process_version_id` | `flow_instance` | 指向 `flow_process_version` 不可变快照；运行时读 `design_json`，草稿编辑/再发布不影响在途实例 |
| 快照 JSON 解析 | Jackson `JsonNode` | `ocr-service` 引擎 | 小型只读访问器封装（取 `props`/`childNode`/`conditionNodes`），不建模型 |
| 业务单据挂接 | `BizSnapshotLoader` 策略接口 | `ocr-service` | `biz_type` → Loader；V1 仅 `LawFirmSelectSnapshotLoader`，后续单据新增实现即可 |
| 推进判定 | **实例级推进锁 + DB 实时查询** | `ocr-service` | 锁 `approval:instance:advance:{instanceId}` 串行化实例内全部流转判定；判定基于任务集实时查询，不维护会签计数冗余字段 |
| 防重复发起 | Redisson 锁 + count | `ocr-service` | 锁 `approval:instance:start:{bizType}:{bizId}`；锁内查 RUNNING 实例存在即 40049 |
| 接口鉴权 | 登录即可（URL 级 `authenticated()`） | `ocr-web` | 运行态是全员能力，不做 `@PreAuthorize`；数据级校验见 §8 |
| 时间/ID 契约 | id 字符串化、时间 `yyyy-MM-dd HH:mm:ss` | 全局 | 与配置域一致（`ToStringSerializer`、GMT+8） |

## 4. 数据模型设计

脚本：`backend/sql/05-approval-runtime-schema.sql`（四表一次执行；02=auth、03=approval、04=lawfirmselect 已占用）。

### 4.1 表：`flow_instance`（审批流程实例表）

```sql
CREATE TABLE flow_instance (
    id                 BIGINT       NOT NULL COMMENT '雪花 ID',
    process_id         BIGINT       NOT NULL COMMENT '流程定义 ID',
    process_code       VARCHAR(64)  NOT NULL COMMENT '流程编码(冗余)',
    process_name       VARCHAR(64)  NOT NULL COMMENT '流程名称(冗余)',
    process_version    VARCHAR(16)  NOT NULL COMMENT '发起时的已发布版本号，如 v2',
    process_version_id BIGINT       NOT NULL COMMENT '流程版本 ID，指向 flow_process_version 不可变快照',
    biz_type           VARCHAR(32)  NOT NULL COMMENT '业务单据类型：LAW_FIRM_SELECT=律所选聘',
    biz_id             BIGINT       NOT NULL COMMENT '业务单据 ID',
    biz_title          VARCHAR(128) NOT NULL COMMENT '业务标题(发起时冗余快照，列表展示)',
    form_snapshot      LONGTEXT     NOT NULL COMMENT '发起时表单数据 JSON 快照(条件求值与详情展示)',
    start_user_id      BIGINT       NOT NULL COMMENT '发起人 ID',
    start_user_name    VARCHAR(64)  NOT NULL COMMENT '发起人名称(冗余)',
    status             VARCHAR(16)  NOT NULL DEFAULT 'RUNNING' COMMENT '状态：RUNNING=进行中 COMPLETED=已完成 REJECTED=已拒绝 CANCELED=已撤销',
    finish_time        DATETIME     DEFAULT NULL COMMENT '结束时间(REJECTED/COMPLETED/CANCELED 时写入)',
    create_time        DATETIME     NOT NULL COMMENT '创建时间',
    update_time        DATETIME     NOT NULL COMMENT '更新时间',
    deleted            TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0=未删 1=已删',
    PRIMARY KEY (id),
    KEY idx_biz (biz_type, biz_id),
    KEY idx_start_user (start_user_id),
    KEY idx_process (process_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='审批流程实例表';
```

取舍：

- **不加 `uk_biz_running` 唯一索引**："同一单据仅一个进行中实例"无法用唯一索引表达（同单据允许存在多条已结束实例）；用发起锁 + 锁内 count 双重兜底（§7.6）。
- **冗余 `process_code/name`、`biz_title`、`start_user_name`**：列表页高频展示，免 join；均为发起时点快照，允许与当前配置脱敏。
- **`form_snapshot` LONGTEXT**：由 `BizSnapshotLoader` 在发起/重新提交时生成（律所选聘 = 单据 DO 序列化 JSON），服务端校验上限（§11），防超大负载。

### 4.2 表：`flow_task`（审批任务表）

```sql
CREATE TABLE flow_task (
    id             BIGINT       NOT NULL COMMENT '雪花 ID',
    instance_id    BIGINT       NOT NULL COMMENT '实例 ID',
    node_id        VARCHAR(64)  NOT NULL COMMENT '节点 ID(WorkflowNode.id)',
    node_name      VARCHAR(64)  NOT NULL COMMENT '节点名称(冗余)',
    assignee_id    BIGINT       NOT NULL COMMENT '审批人用户 ID',
    assignee_name  VARCHAR(64)  NOT NULL COMMENT '审批人名称(冗余)',
    multi_mode     VARCHAR(8)   NOT NULL DEFAULT 'OR' COMMENT '多实例模式快照：OR=或签 AND=会签',
    parent_task_id BIGINT       DEFAULT NULL COMMENT '派生源任务 ID：加签/转办/委托生成，根任务为 NULL',
    status         VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT '状态：PENDING=待办 PASSED=通过 REJECTED=已拒绝 CANCELED=已取消 TRANSFERRED=已转出',
    action         VARCHAR(16)  DEFAULT NULL COMMENT '完成动作：PASS/REJECT/RETURN/TRANSFER/DELEGATE/SUBMIT，PENDING 为 NULL',
    comment        VARCHAR(512) DEFAULT NULL COMMENT '审批意见(任务完成时冗余最近一次)',
    finish_time    DATETIME     DEFAULT NULL COMMENT '完成时间',
    create_time    DATETIME     NOT NULL COMMENT '创建时间',
    update_time    DATETIME     NOT NULL COMMENT '更新时间',
    deleted        TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0=未删 1=已删',
    PRIMARY KEY (id),
    KEY idx_instance_node (instance_id, node_id),
    KEY idx_assignee (assignee_id, status),
    KEY idx_parent (parent_task_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='审批任务表';
```

取舍：

- **会签每人一条任务**（非一任务多候选人）：状态独立、并发安全，推进判定按 `(instance_id, node_id)` 任务集实时计算。
- **`node_id` 为字符串**：与前端 `WorkflowNode.id`（uuid）一致，版本快照内保证唯一。
- **`multi_mode` 快照存任务**：判定时无需回查快照 JSON。
- **转办/委托**：原任务置 `TRANSFERRED`，新任务 `PENDING` 且 `parent_task_id` 指向原任务；会签计数以"根任务的当前活跃替身"为准（§4.6.7）。
- **`comment` 冗余**：任务终态时的最终意见，便于已办列表直显；全量过程意见在 `flow_task_log`。

- 只追加不更新；`AUTO_PASS`/`ENGINE` 为历史版本的系统动作记录（`operator_id=NULL`、`operator_name='系统自动'`），仅存量数据兼容，新数据不再产生；`AUTO_PASS` 仍用于 `flow_task.action`（伪任务）。
- 记录表是**实例详情时间线**（§9.4）的数据源。

### 4.5 状态机与流转总览

**实例状态机**：

```
                    approve(全部节点完成)
        start ──────▶ RUNNING ──────────────────▶ COMPLETED
                       │ │
          cancel(发起人)│ │ reject(无退回目标，终止语义)
                       ▼ ▼
                  CANCELED  REJECTED
```

| 当前状态 | 允许动作 |
|---|---|
| `RUNNING` | 审批动作（审批人）、撤销（发起人）、查看（参与人） |
| `COMPLETED` / `REJECTED` / `CANCELED` | 仅查看；`CANCELED`/`REJECTED` 后单据可重新发起（发起锁内 count RUNNING 自然放行） |

**任务状态机**：

```
                PASS/RETURN/SUBMIT
  挑起任务 ──▶ PENDING ─────────────▶ PASSED
                 │ │
   REJECT(终止/退回) │ │ 或签被抢先 / 驳回级联 / 撤销级联
       REJECTED ◀─┘ └──▶ CANCELED
                 │ TRANSFER/DELEGATE
                 ▼
            TRANSFERRED(新任务顶替)
```

**流转总览**（引擎动作 → 系统行为）：

| 动作 | 触发者 | 系统行为 |
|---|---|---|
| start | 发起人 | 建实例（RUNNING）+ START 日志 + 推进至首个审批节点 + 落抄送 |
| PASS | 审批人 | 任务 PASSED → 判定节点是否完成（或签一票即完/会签全票完/后加签链完）→ 完成则推进下一节点 |
| REJECT | 审批人 | 按节点拒绝配置：`rejectTargetId` → 退回该节点；`canRejectToStart` → 退回发起人；均无 → 实例 REJECTED |
| RETURN | 审批人 | 退回到指定路径节点（或 START=退回发起人重新提交） |
| TRANSFER / DELEGATE | 审批人 | 任务 TRANSFERRED，新任务顶替（同节点、新审批人），日志区分动作 |
| ADD_SIGN | 审批人 | BEFORE：原任务冻结待加签链完成；AFTER：原任务 PASS 后先生成加签链，链完再推进 |
| COMMENT | 任何审批人/发起人 | 仅记日志，任务状态不变 |
| COPY | 审批人/发起人 | 落 `flow_cc`，不影响流转 |
| CANCEL | 发起人 | 实例 CANCELED，全部 PENDING 任务级联 CANCELED |
| SUBMIT（重新提交） | 发起人（驳回到发起人后） | 刷新 `form_snapshot`，从首个审批节点重新推进 |

### 4.6 引擎语义（核心）

#### 4.6.1 发起（start）

1. 取锁 `approval:instance:start:{bizType}:{bizId}`（tryLock(0, 3s)，失败 40045）；锁内查 RUNNING 实例存在 → 40049。
2. 按 `processCode` 查流程：存在且 `status=PUBLISHED` 且 `current_version` 非空 → 否则 40046。
3. **发起范围**：`initiatorType=ALL` 直过；`SPECIFIC` 时 `userId ∈ initiatorMembers` 或用户角色 ∩ `initiatorRoles` 非空 → 否则 40047。
4. `BizSnapshotLoader.load(bizId)`：单据存在且未删 → 否则 40048；`form_snapshot` = 快照 JSON。
5. 落实例（RUNNING）+ START 日志 + 发起时抄送落 `flow_cc` + 释放发起锁 → 推进（§4.6.2）。

> 分支路由**全自动**：推进到 CONDITIONS 时引擎按条件规则配置的英文 `fieldKey` 于 `form_snapshot` 取值求值（§4.6.3），自动判断走哪个分支节点，不存在任何人工选择分支/审批人的交互；SELF_SELECT 来源节点运行时按 §4.6.5 降级处理。

#### 4.6.2 推进（advance）

从某节点出发沿 `childNode` 前行，直到需要人工处理或流程结束：

```
advance(node):
    node == null                        → 到达所在分支链尾 → 分支汇合判定(§4.6.4)
    type == TRANSACT                    → 记 AUTO_PASS 日志，advance(node.childNode)   // V1 办理节点直通
    type == APPROVER                    → 解析审批人(§4.6.5)；生成任务；停止
    type == CONDITIONS                  → 求值(§4.6.3)选定唯一分支 → advance(分支首节点)
    type == CONDITION / PARALLEL_BRANCH → 分支首节点包装层，取其 conditionNodes[0]/首个子节点继续
    type == PARALLEL                    → 每个分支列各 advance(分支首节点)；停止（等待汇合）
    type == START                       → advance(node.childNode)
```

- **主干链尾**（root 链走完且不在任何容器内）→ 实例 `COMPLETED`，写 finish_time。
- **节点完成判定**（每次任务终态后在推进锁内执行）：查 `(instance_id, node_id)` 全部根任务（`parent_task_id IS NULL`）：
  - `multi_mode=OR`：任一根任务链（含其后加签/替身，见 §4.6.7）已完成 → 节点完成，其余 PENDING 根任务级联 CANCELED；
  - `multi_mode=AND`：全部根任务链完成 → 节点完成；
  - 任一任务 REJECTED / RETURN 已触发 → 不做完成判定（退回语义先行处理）。

#### 4.6.3 条件求值（CONDITIONS）

- **分支选择全自动**：引擎按条件规则配置的英文 `fieldKey`（如 `amount`/`title`）于 `form_snapshot` 取值求值，命中即自动走对应分支节点，无任何人工选择交互。
- **求值顺序**：非默认列按 `priority` 升序逐一求值，**首个命中即选定该分支**；全不命中走 `isDefault` 默认列；无默认列（历史导入数据可能）→ 容器**直通**（记 `AUTO_PASS` 日志），advance 到容器 `childNode`。
- **单组求值**（`ConditionGroup`）：组内规则按序以各 `rule.link` 连接（首规则 link 忽略）；组间以 `group.link` 连接（首组忽略）。
- **单规则求值**：`fieldKey` 于 `form_snapshot` 取值；**字段不存在或为 null → 该规则视为不满足**。运算符语义：

| 运算符 | 语义 | 类型处理 |
|---|---|---|
| EQ / NEQ | 相等/不等 | 两值均可解析为数值（`new BigDecimal`，去除多余空格）→ 数值比较；否则字符串比较 |
| GT / GTE / LT / LTE | 大于/大于等于/小于/小于等于 | 双方可解析为数值 → BigDecimal 比较；不可解析 → 该规则不满足 |
| CONTAIN / NOT_CONTAIN | 包含/不包含 | 字符串包含 |

#### 4.6.3.1 人工路由（CONDITIONS `routing=MANUAL`）

支持「上游审批人通过时人工选择下一步」的可选中间环节（如 `a → b → c`，a 也可直接跳 c）。`CONDITIONS` 节点 `props.routing` 取值：

| routing | 语义 |
|---|---|
| `AUTO`（缺省） | 按 §4.6.3 条件规则自动求值选分支（旧数据向前兼容） |
| `MANUAL` | 分支列不配置条件规则，改以 `label` 表达选项名；由上游审批人在 **PASS** 时携带 `routeTargetId`（选中分支列 id）选定 |

- **推进**：PASS 在节点完成后，若链后继为 `MANUAL` 路由节点，则校验 `routeTargetId` 非空（否则 40062）且为该路由节点的合法分支列（否则 40063），从其链首推进；空分支列直通（汇合到容器 `childNode`）。
- **单选语义**：与 AUTO 一致——命中列走完即容器完成，advance 容器 `childNode`（未选中列在进度图中标 SKIPPED）。
- **越权防护**：`routeTargetId` 仅允许指向该人工路由节点自身的分支列，防跳转到流程外节点。
- **指定审批人**：`manualRouteOptions[].assigneeOptions` 返回指定审批人目标节点的候选审批人（优先分支列内首个审批节点；**列内无审批节点（空列或仅直通节点）时回退容器后继链首个审批节点，与空列流转落点一致**；沿链跳过办理等直通节点定位；遇嵌套分支容器为空列表）；非空时前端在选中该分支后渲染可选的「审批人」下拉，选定值经 PASS 的 `routeAssignees`（branchId → userId）回传。引擎校验指定人须在该节点候选集内（否则按 40052 语义拒绝），命中后仅为其创建单人任务（OR 模式）并记系统说明（聚合进本次 PASS 记录 detail）；未指定时按节点默认解析。
- **dryRun 预览**：`next-approvers` 遇 `MANUAL` 节点无法自动选列，返回所有分支列首组审批人（与 PARALLEL 汇聚口径一致）。
- **发布校验**：至少 2 个选项、每列 `label` 非空（前驱不限，见《审批流程配置接口设计》§7.4.1）。上游为非审批节点直连（发起直推/分支汇合后）时无人在 PASS 时选列，引擎降级为自动路由并记系统说明（聚合进触发操作记录 detail）。

#### 4.6.3.2 人工并行（PARALLEL `routing=MANUAL`，多选）

`PARALLEL` 容器 `props.routing` 同样支持 `MANUAL`（缺省 `AUTO`=全部分支无条件并行，旧数据向前兼容）：

- **推进**：PASS 在节点完成后，若链后继为 `MANUAL` 并行节点，则校验 `routeTargetIds` 非空且至少一个（否则 40062）、每个 id 均为该容器的合法分支列（否则 40063），**仅对勾选的分支列并行推进**；空分支列直接参与汇合判定。
- **汇合语义**：未勾选列不创建任务——汇合按「容器全部分支链无 PENDING 任务」判定，天然跳过未勾选列，与 §4.6.4 一致。
- **选项名**：并行分支列直接以节点 `name` 作为下拉选项名（分支名自由编辑，无需 `label`）。
- **指定审批人**：与人工路由同契约——每个勾选分支若有 `assigneeOptions`（优先分支列内首个审批节点，空列回退容器后继链首个审批节点，`routeAssigneeTarget` 统一口径；跳过直通办理节点定位），前端渲染可选「审批人」下拉，`routeAssignees`（branchId → userId）按分支指定；未勾选分支的指定忽略，未指定分支按节点默认解析；**多个空列回退到同一后继节点时，按分支列顺序首个登记生效（putIfAbsent），避免列间互相覆盖**。
- **dryRun 预览**：与 AUTO 并行口径一致，返回全部分支列首组审批人。
- **发布校验**：至少 2 个分支（前驱不限，见《审批流程配置接口设计》§7.4.1）。上游为非审批节点直连时无人在 PASS 时勾选，引擎降级为全列并行并记系统说明（聚合进触发操作记录 detail）。

#### 4.6.4 并行汇合（PARALLEL）

采用**内存回溯法**，不持久化分支进度：任务完成 → 在快照节点树中定位该节点 → 回溯其所属分支列 → 判断该分支链是否走完（分支内所有 APPROVER 节点均已完成判定且无 PENDING 任务）→ 分支走完则检查**同容器所有兄弟分支**是否均走完 → 全部走完 → advance(容器 `childNode`)。回溯算法递归实现，天然支持条件/并行的**任意嵌套**（分支内再遇 CONDITIONS/PARALLEL 按同一逻辑内层优先）。

> CONDITIONS 为**单选**：命中分支链尾完成即视为容器完成，直接 advance 容器 `childNode`（未命中分支节点在进度图中标 SKIPPED）。

#### 4.6.5 审批人解析与空审批人策略

| source | 解析 | 结果为空时 |
|---|---|---|
| `MEMBER` | `memberIds` 直查启用用户 ∪ `roleIds` 展开角色下启用用户，去重 | 走 emptyPolicy |
| `SELF_SELECT` | **降级**：解析结果视为空 + `ENGINE` 日志（detail="SELF_SELECT 已取消人工指定，按空审批人策略处理"） | 走 emptyPolicy |
| `INITIATOR` | 发起人（生成发起人自己的任务；常用于"发起人确认"节点） | 不会为空 |
| `LEADER` | **降级**：解析结果视为空 + `ENGINE` 日志（"LEADER 暂不支持，按空审批人策略处理"） | 走 emptyPolicy |

**emptyPolicy**：

| 策略 | 行为 |
|---|---|
| `AUTO_PASS` | 记 `AUTO_PASS` 日志（detail=审批人为空自动通过），节点直通继续推进 |
| `TO_ADMIN` | ADMIN 角色下全部启用用户按节点 `multi_mode` 生成任务（无 ADMIN 可用用户 → 记 `ENGINE` 日志并抛 `SYSTEM_ERROR`，实例保持 RUNNING 供人工介入） |
| `TO_LEADER` | **降级为 TO_ADMIN** + `ENGINE` 日志，行为同上 |

#### 4.6.6 REJECT / RETURN / CANCEL 语义

- **REJECT**（用户点"拒绝"）：
  - `rejectTargetId` 非空 → **拒绝即退回**：目标节点按其配置重新解析审批人并生成任务；退回点之后所有 PENDING 任务级联 CANCELED；记 `REJECT` 日志（detail=退回到【节点名】）；
  - `rejectTargetId` 为空且 `canRejectToStart=true` → 退回发起人：生成 `node_id=START`、assignee=发起人的 PENDING 任务（发起人后续 PASS=重新提交 / REJECT=终止）；其余 PENDING 级联 CANCELED；
  - 两者均无 → 实例 `REJECTED`，全部 PENDING 级联 CANCELED，写 finish_time。
- **RETURN**（用户主动退回，需选目标 + 审批人 + 方式，2026-10-26 增强）：目标集合对齐前端 `getRejectTargets`（**根到当前节点唯一路径上**先于它的 START/APPROVER——`FlowDesignCursor.findTrail` 与前端 `findTrail` 同构，非路径节点不算上游；`requireReturnTarget` 按此集合强校验，API 直调不可指向并行兄弟分支、未选条件列、后续节点或容器，2026-10-28 修复全树先序误含并行兄弟分支缺陷）。退回动作三要素：
  - **指定审批人 `returnAssignees`**：退回选定目标节点后须为该节点选择审批人——目标为 APPROVER 且候选审批人非空时**必填**（漏传 40069），每人须在 `returnTargets[].assigneeOptions` 候选集内（消费时逐人校验 40057 兜底），登记 `assigneeOverrides` 一次性覆盖默认解析、按节点 `multiMode` 建任务（或签任一人通过 / 会签所选人员均须通过）；目标为 START（发起人重提交任务固定）或候选为空（emptyPolicy 自动通过）时不可传；
  - **退回方式 `returnMode`**：`STEP`（缺省，逐级审批）——目标节点审批通过后从目标节点逐级向前重审，直至再次走到本节点；`DIRECT`（审批后直达本节点）——目标节点审批通过（含退回 START 后重提交、目标节点空审批人 AUTO_PASS）后**跳过中间节点**，直接在本节点（退回发起节点）重建审批任务。退回按次落 **`flow_return_record` 记录表**（脚本 `07-return-enhance-schema.sql`）：`{instanceId, fromTaskId, fromNodeId, targetNodeId, returnMode, status}`，状态机 `PENDING`（DIRECT 待直达）→ `CONSUMED`（目标完成已直达）/ `RESET`（拒绝退回重走、实例终态清理）/ `FINISHED`（STEP 纯审计）。消费规则：节点完成时 `consumeDirectReturn` 查 `status=PENDING 且 target=完成节点` 的记录**逐条**置 CONSUMED 并在各自 from 节点重建任务（`doPass` 节点完成判定后与 `resolveApproverAndCreate` AUTO_PASS 分支两处拦截），系统说明记「退回直达，跳过中间节点」；记录按次插入互不覆盖——**接力退回嵌套直达**（a1→X 后 X→Y：Y 完成直达 X，X 完成再直达 a1，两条意图都生效），列表消费口径为并行各自退回（预留）天然兼容；**唯一退回目标为发起人**（当前节点即首个审批节点）时，前端面板省略退回节点与退回方式选择——此时无中间节点可跳，DIRECT 与 STEP 等价，固定缺省 STEP 并自动定向发起人目标（后端无特殊分支，`targetNodeId` 照常必填）；
  - **级联取消**：退回是「回到过去」——实例内全部剩余 PENDING 任务（本节点或签/加签链、并行其它分支、更下游节点）一并 CANCELED（`cancelInstancePendingTasks`，修复此前仅取消本节点导致并行分支残留的缺陷；REJECT 退回同口径）；退回日志 detail 记「退回到【节点名】（审批后直达本节点/逐级审批）」。
  退回到 START 的重提交语义不变（发起人 PASS=重新提交，从首节点重新推进；DIRECT 时重提交后直达本节点）。
- **CANCEL**（发起人撤销）：仅 `RUNNING`；实例 `CANCELED`，全部 PENDING 级联 CANCELED，写 finish_time。
- **重新提交（SUBMIT）**：发起人处理"退回发起"任务时 PASS → **重新加载单据快照**（经 `BizSnapshotLoader`）覆盖 `form_snapshot` → 从首个审批节点重新推进（条件重新求值，历史记录保留）；REJECT → 实例 `REJECTED`。

#### 4.6.7 加签与转办的任务链

任务链以 `parent_task_id` 组织，节点完成判定只看**根任务链**：

```
根任务(R) ──TRANSFER──▶ 替身任务(T, PENDING)        # R=TRANSFERRED；判定以 T 为准
根任务(R) ──ADD_SIGN_BEFORE──▶ 前加签链 B1→B2…        # 链未完成时 R 冻结(PENDING 但不参与判定)
根任务(R) ──ADD_SIGN_AFTER──▶ 后加签链 A1→A2…        # R 已 PASSED，链完成后节点才完成
```

- **前加签**：加签任务 PENDING（assignee=被加签人）生成，原任务保持 PENDING 但**冻结**；加签链全部 PASSED → 原任务解冻待办；加签链 REJECTED → 按 §4.6.6 REJECT 语义处理（退回/终止）。
- **后加签**：原任务 PASS 后**不推进节点**，先生成后加签任务；后加签链全部 PASSED → 节点完成推进；链上 REJECTED → 按 REJECT 语义处理。
- **链上加签**：加签任务上再加签，沿 `parent_task_id` 链判定"链完成"= 链上全部任务终态且末位 PASSED，递归自然支持。
- **会签 + 加签**：会签计数仅统计根任务链（替身顶替原根任务），加签不改变票数，仅延长链。
- **减签（REDUCE_SIGN，2026-10-19）**：发起加签人（根任务 assignee，任务 PENDING）可删除自己直接派生且 PENDING 的加签任务（`targetTaskId` 指定，BEFORE_SIGN/AFTER_SIGN 均可）；目标任务之下若有 PENDING 链上加签子任务则级联取消。根任务仍 PENDING → 节点必未完成，无需推进判定：前加签链清空即原任务解冻可办；后加签删除后原任务 PASS 按正常链路推进。落一条 REDUCE_SIGN 审批记录（detail=「减签，移除加签人【XXX】」，含链时注明共 N 项）。任务详情接口返回 `pendingSignTasks`（当前任务直接派生且 PENDING 的加签任务，含加签人姓名/方向），同意弹窗据此提示「加签人还没有同意」并提供删除按钮——减签成功后弹窗保持打开、列表实时更新。

#### 4.6.8 动作可用性校验

- `PASS/REJECT/TRANSFER/DELEGATE/ADD_SIGN/RETURN` 必须在节点 `buttons` 中对应项 `enabled=true`（按钮 key 映射：ADD_SIGN + direction → `ADD_SIGN_BEFORE`/`ADD_SIGN_AFTER`）→ 否则 40058；
- **前加签任务动作白名单**：`signType=BEFORE_SIGN` 的任务仅允许 `PASS/COMMENT/COPY`，其余动作（REJECT/RETURN/TRANSFER/DELEGATE/ADD_SIGN）一律 40058；任务详情接口对其只下发 PASS 按钮（文案沿用节点配置，缺省「同意」，评论恒可用），`manualRouteOptions`/`returnTargets` 置空——前加签人 PASS 后任务回到原审批人，节点后继的人工路由（CONDITIONS/PARALLEL MANUAL）由**原审批人** PASS 时选择，加签人不参与选路（2026-10-19）；
- `REDUCE_SIGN` 不受节点按钮配置约束（加签的逆操作，操作主体须为派生源任务的 assignee 且源任务 PENDING）：`targetTaskId` 须为该任务直接派生且 PENDING 的加签任务（BEFORE_SIGN/AFTER_SIGN），否则 40064；
- `COMMENT/COPY` 不受按钮配置约束（始终可用）；
- `RETURN` 的可选目标由任务详情接口返回（§9.9），仅 `RETURN` 按钮启用且目标非空时可操作；
- 操作人必须为任务 `assignee` 且任务 PENDING → 否则 40054/40055。

### 7.6 并发控制（Redisson）

| 锁 key | 粒度 | 场景 | 冲突行为 |
|---|---|---|---|
| `approval:instance:start:{bizType}:{bizId}` | 单据 | 发起（含校验 + 建实例） | 40045 |
| `approval:instance:advance:{instanceId}` | 实例 | **全部**任务动作 / 撤销 / 重新提交（引擎内） | 40045 |

- 均为 `tryLock(0, 3, SECONDS)` + `finally` 中 `isHeldByCurrentThread` 释放，复用 `ApprovalProcessProperties.lockLeaseSeconds`（§11 配置）。
- 实例级推进锁串行化同一实例的全部流转判定（或签两审批人并发提交、会签末票与抄送并发等），判定基于锁内 DB 实时查询，**不维护计数冗余**，彻底规避竞态；实例操作频率低，锁无性能瓶颈。

## 8. 安全设计要点

| 主题 | 设计 |
|---|---|
| 数据级越权 | 待办/已办/我发起的/待阅列表一律 `assignee_id/start_user_id/receiver_id = 当前用户` 过滤；动作接口校验 `assignee`（40054）；撤销校验发起人；详情可见性 = 发起人 ∪ 历史任务审批人 ∪ 抄送接收人 ∪ ADMIN（40059） |
| 垂直越权 | 运行态无管理能力，无需 ADMIN 收口；ADMIN 仅作为详情可见性兜底 |
| 状态机约束 | 全部写操作先 `selectById` 校验状态（PENDING/RUNNING）再执行，推进锁 + `@Transactional(rollbackFor = Exception.class)` 包裹动作与级联 |
| SQL 注入 | 全部 `LambdaQueryWrapper`；无动态拼接 |
| 超大负载 | `form_snapshot` 上限 512KB（发起/重新提交时校验）；`comment` 长度列级约束 + DTO 校验 |
| 重复发起 | 发起锁 + 锁内 RUNNING count 双重兜底（单据维度串行化） |
| 单据篡改 | `LawFirmSelectServiceImpl.update/remove` 前置校验无 RUNNING 实例（40060），保证 `form_snapshot` 与单据一致 |
| 目标人员校验 | 转办/委托/加签/抄送目标必须为存在且启用用户（40057）；上限校验（`max-receivers`，默认 20） |
| 按钮级权限 | 节点 `buttons.enabled` 决定动作可用性（40058），服务端强校验，防前端绕过 |

### 9.12 下一节点审批人预览 `POST /api/approval/instance/next-approvers`

> 查询语义但采用 POST：入参含 Map 结构（`conditions`），放 RequestBody 传原生 JSON 对象，避免 URL 编码 JSON 字符串；无副作用、幂等。

请求 Body（`NextApproverQueryDTO`）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| processId | string | 是 | 流程定义 ID |
| nodeId | string | 否 | 当前节点 ID；**缺省时默认返回发起后第一个审批节点的审批人** |
| conditions | map<string, string> | 否 | **条件值 Map**：键为条件规则的英文 `fieldKey`，值为条件值；序列化后 ≤4KB，用于 CONDITIONS 真实求值 |

```json
{ "processId": "1860000000000000001", "nodeId": null,
  "conditions": { "amount": "60000", "title": "XX律师事务所选聘" } }
```

**语义**：从给定节点的**后继**（`nodeId` 缺省则从 root 后继）模拟推进（§4.6.2 同款遍历，无副作用 dryRun），返回下一组需要人工处理的 APPROVER 节点及其解析后的审批人清单。推进与解析规则与运行时完全一致：

- 跳过 START/TRANSACT（直通）；
- CONDITIONS：**传 `conditions`（条件值 Map）时按 §4.6.3 真实求值**——`fieldKey` 于 Map 取值（Map 中缺失的键视为该规则不满足），命中即走对应分支，全不命中走默认列，无默认列直通；**未传 `conditions` 时按默认列（isDefault）模拟**（实际路由以发起时 `form_snapshot` 求值为准）；
- PARALLEL 并行激活：返回**各分支各自的**首个审批节点（`nodes` 为多元素）；
- 审批人解析同 §4.6.5：MEMBER 展开、INITIATOR=当前登录用户、SELF_SELECT/LEADER 降级、TO_LEADER→TO_ADMIN；空审批人 AUTO_PASS 节点跳过继续向后找；
- SUB_PROCESS：WAIT 节点穿透进入 subDoc 取子流程首个审批节点（子链走完才继续父 `childNode`）；IMMEDIATE 节点子实例旁路启动，子 doc 首组审批人与父 `childNode` 首组审批人一并返回（两路并行，与运行态一致）；
- 推进到链尾无审批节点 → `ended=true`、`nodes` 为空数组（前端显示"通过后流程结束"）。

响应 `data`（`NextApproverVO`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| ended | boolean | true=后续无审批节点（nodes 为空数组） |
| nodes | `NodeApproverPreviewVO[]` | 下一审批节点组（线性流程恒 1 个；并行激活时多个） |

`NodeApproverPreviewVO`：`{ nodeId, nodeName, multiMode, scopeType, scopeName, approvers: [{ userId, name }] }`。其中 `scopeType` 标识节点归属（`MAIN`=主流程 / `SUB_PROCESS`=子流程），`scopeName` 为归属流程名称（主流程名或子流程节点名）；前端提交抽屉据此区分主/子流程审批人并在标题与节点名处标注（子流程 IMMEDIATE 场景下一节点同时含两类节点）。

```json
{
  "code": 0, "message": "成功", "timestamp": 1780000000000,
  "data": {
    "ended": false,
    "nodes": [ { "nodeId": "n-a1b2", "nodeName": "部门审批", "multiMode": "OR",
                 "approvers": [ { "userId": "1001", "name": "张三" }, { "userId": "1002", "name": "李四" } ] } ]
  }
}
```

失败：`40046` 流程不存在或未发布、`40061` 流程节点不存在、`40000` Body 结构非法或 `conditions` 键值超长。

> **前端用途**：发起弹窗选定流程后调用（不传 `nodeId`，可带表单当前值作为 `conditions`）展示"提交后将由以下人员审批"；办理页/任务详情以当前节点 id 调用（可带单据快照字段作为 `conditions`）展示"通过后由下一节点审批人处理"。新增单据"提交审批"抽屉（`SubmitApprovalDrawer`，2026-10-19 简化）**固定不传 `nodeId`、仅设置第一审批阶段（下一节点）审批人**，不再提供"预览起点"切换查看/设置下下节点；下一阶段为 PARALLEL 并行（`nodes` 多元素）时按节点名称分行、各节点独立下拉分别选择（或签单选 / 会签多选）；IMMEDIATE 子流程场景展示主/子流程双线节点。所选审批人经发起接口 `startAssignees` 真实生效（2026-10-23 起替代"预演性质"，修复提交时选 2 人待办出现 3 人的缺陷——选择此前未随请求下发）。

### 9.15 新增并提交审批（组合接口，2026-10-19 新增）`POST /api/law-firm-select/create-and-submit`

**动机**：新增单据"直接提交"原由前端串两次请求（`/law-firm-select/create` → `/approval/instance/start`），两次 HTTP 之间无事务边界，`create` 成功而 `start` 失败（流程未发布/无发起权限/网络中断）会残留孤儿单据。**独立 HTTP 请求之间不存在数据库事务**，唯一正确解法是后端收敛为单请求单事务。

**事务与并发设计**（`LawFirmSelectServiceImpl.createAndSubmit`）：

- 外层：用户级 Redisson 防重锁 `approval:law_firm_select:create_submit:{userId}`（`tryLock` 非阻塞，拿不到 → 40045；lease 复用 `approval.runtime.lock-lease-seconds`），**锁包住事务**，事务提交后才释放，防双击重复建单；
- 内层：`TransactionTemplate.execute`（PROPAGATION_REQUIRED）同一事务内完成 `insert law_firm_select` + 复用 `FlowInstanceService.start`（内部嵌套锁可重入、引擎 `startInstance` 的嵌套事务模板同传播级别，全部加入外层事务）；
- 发起任一校验失败抛 `BusinessException` → 建单 insert 一并回滚，**不残留草稿**；
- `bizType` 由后端固定 `LAW_FIRM_SELECT`，不信任前端传值（组合入参不含 bizType/bizId）。

Body：`LawFirmSelectSubmitDTO` = 单据字段（title/amount/reason，校验同 `LawFirmSelectSaveDTO`）+ 发起字段（processCode 必填、ccUserIds ≤20 可选、comment ≤512 可选、startAssignees 可选〔nodeId → userIds，2026-10-23 新增，透传 `InstanceStartDTO.startAssignees`，抽屉预览区所选审批人经此生效〕）。成功返回 `data` = 实例 ID（字符串）。

**前端配套**：新增页 `SubmitApprovalDrawer` 确认提交改调 `submitLawFirmSelectCreateAndSubmit`（`src/api/lawfirmselect.ts`），组件删除已无用的 `bizType` prop；列表页 `StartApprovalDialog`（已有 bizId 的单据发起）维持 `/approval/instance/start` 不变，两条路径并存。

## 14. 风险与取舍

| 风险/取舍 | 影响 | 应对 |
|---|---|---|
| LEADER/TO_LEADER 降级 | 主管审批场景暂不可用 | 降级路径全部 `ENGINE` 日志可审计；V2 引入 `sys_org.leader_id` 或用户汇报线后，仅改 `resolveAssignees` 一处 |
| SELF_SELECT 取消人工指定 | "按单据内容动态指定审批人"须以条件分支表达 | 用户决策：条件规则按英文 `fieldKey` 匹配 `form_snapshot` 自动选路，各分支下接不同审批人节点；SELF_SELECT 节点运行时降级 emptyPolicy + `ENGINE` 日志，不阻塞流程 |
| DELEGATE=转办语义 | 委托人名下"仍算本人"的语义缺失 | V1 明示简化；V2 若需，以"替身任务完成人=受托人 + 日志归属"扩展 |
| 推进判定实时查询（无计数冗余） | 每次动作多几条查询 | 实例任务量小 + 实例级推进锁天然限流；量大时再加节点级聚合缓存 |
| 并行汇合内存回溯 | 每次任务完成重算路径 | 快照 JSON 级别内存计算，量级可控；算法递归支持任意嵌套 |
| 条件字段无注册机制 | `fieldKey` 靠约定（单据快照键名） | 前端条件规则配置的输入即字段名，配置域发布校验不拦截未知字段（运行时字段缺失规则不满足，行为安全） |
| 无消息通知 | 待办不主动触达 | V2 通知域（站内信/WebSocket）另立设计 |
| `form_snapshot` 与单据一致性强依赖编辑拦截 | 拦截面仅律所选聘一处（现状唯一 biz） | `BizSnapshotLoader` + `BIZ_IN_APPROVAL` 前置校验模式随新单据复制 |
| 抄送进入详情自动标记已阅 | 未真正细读也可能标记 | 与钉钉一致的简化体验；后续可改为滚动到底才标记 |
| 审批中单据新字段变化不反映在详情 | 详情展示的是发起时快照 | 属预期语义（流程评审的是发起时点数据），详情页文案说明"以下为发起时表单内容" |

| 引擎遍历快照不建 Java 模型 | 无法做节点级静态分析 | 与配置域策略一致；运行期校验（动作可用性/退回目标/进度推导）全部基于同一 `FlowDesignCursor`，收敛单点 |

## 15. 子流程节点（SUB_PROCESS）扩展指引（2026-10-22）

新增节点类型 **`SUB_PROCESS`（子流程）** 的运行态语义（完整设计见《工作流子流程节点设计.md》）：

- **子实例同表**：`flow_instance` 增 `parent_instance_id/parent_node_id/root_instance_id/depth/design_json`（脚本 `06-sub-process-schema.sql`）；身份字段继承父实例，`process_name={父流程名}·{子流程节点名}`，`design_json` 冗余存父快照内 `subDoc`（`loadDesign` 统一口径：根读版本表、子读冗余列）；
- **流转**：`advance` 遇 SUB_PROCESS → 自动建子实例并推进其首个审批节点（父实例等待、无任务）；子实例主干链尾 COMPLETED → 回推父 `SUB_PROCESS.childNode`；子实例 REJECT 终止 → 祖先链逐级 REJECTED；根撤销/终止 → 按 `root_instance_id` 树级联取消（`cascadeTreeTerminal`）；
- **树级推进锁**：锁 key 由 `{instanceId}` 改为 **`{rootInstanceId}`**，规避父↔子交叉加锁死锁；发起锁内 40049 判定改**根实例口径**（`parent_instance_id IS NULL`）；
- **既有语义作用域=当前 doc**：会签/加签/退回目标/驳回到发起人等均限定子实例内部，`INITIATOR` 穿透为根发起人，`form_snapshot` 与父共享；分支列内禁止 SUB_PROCESS（发布校验 40067）；
- **接口**：无新增 URL；`mine`/`biz-status` 仅根实例，待办/已办子流程任务加 `subProcessName` 徽标，详情增 `subInstances[]`/`parentInstanceId`，直接撤销子实例 40068；`next-approvers` 穿透 subDoc（WAIT 穿透子 doc、IMMEDIATE 子 doc 与父 childNode 首组审批人一并返回）。
- **审批通过指定主/子流程审批人（2026-10-23）**：当前节点链后继为 `SUB_PROCESS` 且 `advanceMode=IMMEDIATE` 时，任务详情下发 `subProcessApproverOptions`（子流程首节点 + 父链下一节点，含 `scopeType`/`scopeName`/`assigneeOptions`），PASS 携带 `subProcessAssignees`（nodeId → userId）分别指定；引擎登记到 `assigneeOverrides`——父链节点由父链推进消费，子流程节点在 `buildSubInstance` 复制到子上下文消费（nodeId 全局唯一逐节点定位），校验口径与 `routeAssignees` 一致（候选集内，否则 40052 语义拒绝）。
