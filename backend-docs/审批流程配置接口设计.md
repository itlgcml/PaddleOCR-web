### 1.1 术语与实体关系约定

| 实体 | 关系 | 说明 |

## 2. 目标与范围

### 2.1 本期（V1）

1. **流程定义 CRUD**：新增（基本信息，初始草稿）、更新基本信息、分页查询、详情、逻辑删除（仅草稿态）。
2. **流程设计持久化**：保存流程设计 JSON（`WorkflowDoc`）草稿，与已发布版本快照**分字段存储**；查询流程设计（缺省草稿，支持指定已发布版本）。
3. **版本管理**：每次发布生成新版本（v1/v2/v3…），同一时刻仅一个已发布版本；草稿保存不产生新版本；版本列表、按版本查询历史设计。
4. **状态机**：`DRAFT → PUBLISHED → DISABLED`，停用后可再发布；发布前服务端校验流程设计合法性（对齐前端 `useWorkflowValidate`）。
5. **权限**：流程配置域为管理端能力，全部接口 `@PreAuthorize("hasRole('ADMIN')")`。

### 2.2 明确不做（避免过度设计）

| 项 | 决策 | 理由 |
|---|---|---|
| 发起/待办/已办/待阅/已阅（前端二级菜单占位页） | V2 预留 | 本期聚焦「流程配置」域；发起、审批流转、我的申请等属流程运行态，需先有实例模型（`flow_instance`/`flow_task`），独立设计 |
| 流程实例运行引擎 | V2 | 需设计实例表、任务表、审批动作、条件/并行节点执行语义，量级大，另立专项 |
| 多人审批/条件分支的运行时计算 | V2 | 本期只存 `WorkflowDoc` JSON，不做节点级运行时解析与路由 |
| 流程设计可视化节点的服务端反序列化建模 | 不做 | 前端已用 JSON 自描述（`WorkflowDoc`），服务端以 `LONGTEXT` 存原文 + 发布时做最小结构校验，不逐节点落表 |
| 发起人范围与 `sys_role`/`sys_user` 的强关联外键 | 不做 | `initiator_members`/`initiator_roles` 存 ID JSON 数组（人员/角色 ID 字符串），不做外键级联校验；如需 DB 级引用完整性留 V2 |

## 3. 技术选型

| 能力 | 选型 | 放置 | 说明 |
|---|---|---|---|
| 持久层 | MyBatis-Plus `BaseMapper` | `ocr-dal` | 两张表各一个 DO + Mapper，无 join 需求不写 XML |
| 主键 | 雪花 ID `IdType.ASSIGN_ID` | `ocr-dal` | 与既有 `OrgDO` 等一致；`Long` 序列化为字符串 |
| 流程设计 JSON 存储 | `LONGTEXT` × 2 | `flow_process.draft_json`（草稿编辑区）/ `flow_process_version.design_json`（发布快照） | 草稿与发布分离存储；存 `WorkflowDoc` 完整 JSON，前后端契约零转换 |
| 发起范围存储 | `VARCHAR(16)` + 两个 `VARCHAR(512)` JSON 数组 | `flow_process.initiator_type` / `initiator_members` / `initiator_roles` | `ALL`/`SPECIFIC` 二态 + 人员/角色 ID 数组；量级小无需关联表 |
| 前端路径存储 | `VARCHAR(200)` 单值列 | `flow_process.start_path` / `detail_path` | 前端发起/详情路由，必填，以 `/` 开头 |
| 状态/版本号存储 | `VARCHAR(16)` 英文枚举 | `status` / `version` / `current_version` | 与前端 `draft/published/disabled`、`v1/v2/v3` 契约一致，避免数字魔法值 |
| 分页 | `PageResultVO<T>` | `ocr-service/model` | 复用现有分页 VO |
| 接口鉴权 | `@PreAuthorize("hasRole('ADMIN')")` | `ocr-web` | 流程配置为管理端能力，复用现有 `SecurityConfig` 的方法级鉴权 |
| 接口文档 | springdoc `@Tag` / `@Operation` | `ocr-web` | 与既有 Controller 一致 |
| 防重复提交 | **Redisson 分布式锁** | `redisson-spring-boot-starter` 3.17.7（JDK 8 兼容线）→ `ocr-service` | 保存设计 / 发布接口用 `RLock` 对 `approval:process:submit:{id}` 加锁，`tryLock` 失败返回 40045；Redis 复用 auth 已引入实例 |

## 4. 数据模型设计

脚本：`backend/sql/03-approval-schema.sql`（两张表一次执行；`02` 编号已被 auth 占用，见 `backend-docs/用户注册与登录功能.md` §4）。

### 4.1 表：`flow_process`（审批流程定义表）

```sql
CREATE TABLE flow_process (
    id              BIGINT       NOT NULL COMMENT '雪花 ID',
    code            VARCHAR(64)  NOT NULL COMMENT '流程编码，业务唯一',
    name            VARCHAR(64)  NOT NULL COMMENT '流程名称',
    description     VARCHAR(255) DEFAULT NULL COMMENT '流程描述',
    start_path      VARCHAR(200) NOT NULL COMMENT '前端发起路径，以 / 开头',
    detail_path     VARCHAR(200) NOT NULL COMMENT '前端详情路径，以 / 开头',
    initiator_type  VARCHAR(16)  NOT NULL DEFAULT 'ALL' COMMENT '发起范围：ALL=全体 SPECIFIC=指定',
    initiator_members VARCHAR(512) NOT NULL DEFAULT '[]' COMMENT '指定人员 ID(JSON 数组，SPECIFIC 时生效)',
    initiator_roles   VARCHAR(512) NOT NULL DEFAULT '[]' COMMENT '指定角色 ID(JSON 数组，SPECIFIC 时生效)',
    status          VARCHAR(16)  NOT NULL DEFAULT 'DRAFT' COMMENT '状态：DRAFT=草稿 PUBLISHED=已发布 DISABLED=已停用',
    current_version VARCHAR(16)  DEFAULT NULL COMMENT '当前已发布版本号，如 v1；从未发布时为 NULL',
    draft_json      LONGTEXT     DEFAULT NULL COMMENT '草稿流程设计 JSON(WorkflowDoc)，编辑保存区，与发布快照分离',
    create_time     DATETIME     NOT NULL COMMENT '创建时间',
    update_time     DATETIME     NOT NULL COMMENT '更新时间',
    deleted         TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0=未删 1=已删',
    PRIMARY KEY (id),
    UNIQUE KEY uk_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='审批流程定义表';
```

取舍：

- **`uk_code` 不含 `deleted`**：流程编码逻辑删除后不可复用，与 `sys_user.uk_username` 同策略，防"删后同名查到历史数据"。
- **发起范围拆为 type + 两个 JSON 文本列而非关联表**：`ALL`/`SPECIFIC` 二态 + 人员/角色 ID 数组（与前端 `StartProps` 契约一致：`rangeType/memberIds/roleIds`），不做 `sys_user`/`sys_role` 外键；V2 若需引用完整性再拆 `flow_process_initiator` 关联表。
- **`start_path`/`detail_path` NOT NULL**：前端两路径为必填项（默认写死示例值 `/approval/leave/create`、`/approval/leave/detail`），后端同步非空 + 以 `/` 开头校验。
- **`status` / `version` 用 `VARCHAR` 存英文枚举**：与前端契约（`draft/published/disabled`、`v1/v2/v3`）直映射，避免数字状态码在前后端各维护一份映射表。
- **`current_version` 冗余**：列表/详情直接回显当前已发布版本号，避免每次 join 版本表；仅由发布动作维护。
- **草稿与发布快照分字段存储**：`draft_json` 是唯一编辑区（保存只覆盖它），`flow_process_version.design_json` 是发布时冻结的不可变快照 → 已发布的 `v1` 仍可继续编辑保存，不发布就永远不产生 `v2`，且编辑不影响 `v1` 快照。

### 4.2 表：`flow_process_version`（审批流程版本表）

```sql
CREATE TABLE flow_process_version (
    id          BIGINT      NOT NULL COMMENT '雪花 ID',
    process_id  BIGINT      NOT NULL COMMENT '流程定义 ID',
    version     VARCHAR(16) NOT NULL COMMENT '版本号，如 v1/v2/v3',
    design_json LONGTEXT    NOT NULL COMMENT '发布时冻结的流程设计 JSON 快照(WorkflowDoc，不可变)',
    create_time DATETIME    NOT NULL COMMENT '创建时间',
    update_time DATETIME    NOT NULL COMMENT '更新时间',
    deleted     TINYINT     NOT NULL DEFAULT 0 COMMENT '逻辑删除 0=未删 1=已删',
    PRIMARY KEY (id),
    UNIQUE KEY uk_process_version (process_id, version),
    KEY idx_process_id (process_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='审批流程版本表';
```

取舍：

- **版本表只存已发布快照**：版本记录仅在发布时创建，`design_json` 为当时草稿的冻结副本；草稿编辑不落此表（存 `flow_process.draft_json`）。
- **`uk_process_version(process_id, version)`**：一个流程同一版本号唯一，版本号由服务端单调递增生成，防并发重复。
- **已发布版本不可变（immutable）**：发布后 `design_json` 禁止任何 update；后续编辑一律作用于草稿字段，再次发布生成新版本。

### 4.3 状态机与版本策略

**状态机**：

```
        publish                 disable
 DRAFT ────────▶ PUBLISHED ──────────────▶ DISABLED
   ▲                                         │
   └─────────────── publish ─────────────────┘
```

| 当前状态 | 允许动作 |
|---|---|
| `DRAFT` | 编辑基本信息、保存/覆盖草稿设计、发布、删除 |
| `PUBLISHED` | 停用、**继续编辑并保存草稿设计**（不影响已发布快照）、发布（产生新版本）、查看 |
| `DISABLED` | 编辑并保存草稿设计、发布（基于草稿生成新版本并回到 `PUBLISHED`）、查看 |

> 简化约定：**草稿设计（`draft_json`）任意未删除状态均可保存**——保存永不产生新版本、永不影响已发布快照；基本信息编辑仍仅 `DRAFT` 态。已发布流程的修改路径：直接编辑草稿 → 再次发布生成新版本。

**版本策略**：

| 动作 | 版本行为 |
|---|---|
| 新增流程 | 无版本，`current_version = NULL`、`draft_json = NULL`，状态 `DRAFT` |
| 保存流程设计（草稿） | 仅覆盖 `flow_process.draft_json`；版本号不变、**不产生新版本**、不影响任何已发布快照 |
| 发布 | 校验 `draft_json` 合法（§7.4）→ 生成新版本 `v{n+1}`（`design_json` = 校验通过的草稿内容，落库后不可变）→ `current_version = v{n+1}`、流程状态置 `PUBLISHED` |
| 再发布（DISABLED→PUBLISHED） | 与发布一致：基于当前草稿生成新版本（草稿未改动则快照内容与上一版本相同，版本号仍递增） |

**草稿 / 发布分离存储的关键语义**：

- 已发布版本 `v1` 后继续编辑保存：只写 `draft_json`，只要不发布就永远没有 `v2`，且 `v1.design_json` 保持发布时的内容不变。
- 同一时刻**只有一个已发布版本**（`current_version` 指向），其余版本均为历史快照。
- 运行态（V2 流程实例）一律引用 `current_version` 指向的快照，与草稿编辑完全隔离。

## 6. 错误码设计

`ResultCode` 追加（沿用分段：0 成功 / 4xxxx 客户端 / 5xxxx 系统 / 503xx OCR），审批流程段取 **40040 起**：

| 枚举 | code | message | 触发场景 |
|---|---|---|---|
| `PROCESS_CODE_EXISTS` | 40040 | 流程编码已存在 | 新增流程撞 `uk_code`（含并发兜底） |
| `PROCESS_NOT_FOUND` | 40041 | 流程不存在 | 目标流程查无/已删 |
| `PROCESS_DESIGN_INVALID` | 40042 | 流程设计不合法 | 发布时 `design_json` 未通过最小结构校验（§7.4） |
| `PROCESS_STATUS_ILLEGAL` | 40043 | 流程状态不允许该操作 | 非 `DRAFT` 态编辑/删除；非 `PUBLISHED` 态停用 |
| `PROCESS_VERSION_NOT_FOUND` | 40044 | 流程版本不存在 | 按版本查询设计时查无该版本 |
| `PROCESS_REPEAT_SUBMIT` | 40045 | 请勿重复提交 | 保存设计 / 发布接口并发重复提交（分布式锁未获取） |

**HTTP 状态码策略**：业务响应一律 HTTP 200 + `code` 非零；鉴权失败沿用现有 401/403 通路（`code` ∈ 40100~40103/40300），本章节不重复。并发撞唯一索引由 `GlobalExceptionHandler` 的 `DuplicateKeyException` 映射 `uk_code → 40040`、`uk_process_version → 40042`（版本号生成冲突按系统异常处理，见 §13）。

## 7. 核心类设计

### 7.1 `ocr-dal`：两张表实体类

**注解规范**（与既有 DO 一致）：表名 `@TableName`、表中文名类级 `@Schema`、字段中文名 + 长度字段级 `@Schema`、主键 `@TableId(type = IdType.ASSIGN_ID)` + `@JsonSerialize(ToStringSerializer)`、审计字段 `@TableField(fill = ...)`、逻辑删除 `@TableLogic`。

#### `ProcessDO`（`flow_process`，审批流程定义表）

    @Schema(description = "指定人员 ID(JSON 数组，SPECIFIC 时生效)", maxLength = 512)

### 7.4 发布校验（`design_json` 最小结构校验，对齐前端 `useWorkflowValidate`）

发布时对 `design_json`（`WorkflowDoc`）做**最小结构校验**，任一不满足抛 `BusinessException(PROCESS_DESIGN_INVALID)`：

| 规则 | 对应前端逻辑 |
|---|---|
| `design_json` 非空且可解析为 `{ name, root }` | `loadDoc` 的基础校验 |
| `root.type == "START"` | 前端 `loadDoc` 要求根节点为 START |
| 遍历节点：`name` 非空 | `useWorkflowValidate` 的「存在未命名的节点」 |
| 遍历节点：`APPROVER` 节点 `source == "MEMBER"` 时 `memberIds` 与 `roleIds` 的并集非空（前端已支持审批人同时指定人员与角色） | 「审批节点未选择审批人」 |
| `CONDITION` 节点：非 `isDefault` 且无规则 → 报错 | 「条件未配置规则」 |
| `CONDITIONS` 节点 `routing == "MANUAL"`（人工路由）时：分支列数 ≥ 2、每列 `label` 非空（前驱不限：审批人直连时由其 PASS 选路，非审批人直连时运行态降级自动路由） | 「人工路由节点配置不合法」 |
| `PARALLEL` 节点 `routing == "MANUAL"`（人工并行）时：分支列数 ≥ 2（前驱不限；非审批人直连时运行态降级全列并行；选项名直接用分支列 `name`，无 `label` 要求） | 「人工并行节点配置不合法」 |
| `CONDITION` 节点（所属容器 `routing == "MANUAL"`）：不做规则校验，改校验 `label` 非空 | 「选项未配置名称」 |

> 校验用通用 JSON 解析（`com.fasterxml.jackson` 或 `org.json`），**不逐节点建 Java 模型**；只做"能否通过"判断，不解析节点语义（V2 运行时引擎再深挖）。

#### 7.4.1 人工路由节点契约（`routing = "MANUAL"`）

支持「上游审批人通过时人工选择下一步」的可选中间环节（如 `a → b → c`，a 也可直接跳 c）：

- `CONDITIONS` 节点 `props` 增加 `routing: "AUTO" | "MANUAL"`（旧数据缺省按 `AUTO`，向前兼容）。
- `MANUAL` 模式下 `conditionNodes` 各分支列（`CONDITION`）以 `props.label` 表达**选项名**，不再配置条件规则；`isDefault`/`priority` 失去语义（引擎不读取）。
- 结构示例：`a(APPROVER) → CONDITIONS(routing=MANUAL) { 列1「发给B」→ b(APPROVER)；列2「直接发C」→ 空(直通) } → childNode = c(APPROVER)`，选列1走 b 后汇合到 c，选列2直通汇合到 c。
- 运行态选择动作由 `PASS` 携带 `routeTargetId`（选中分支列 id）完成，见《工作流提交与审批操作接口设计》§4.6.3.1。

**人工并行（`PARALLEL` 同样支持 `routing = "MANUAL"`，多选）**：

- `PARALLEL` 容器 `props.routing` 取值同上：`AUTO`（缺省）=全部分支无条件并行；`MANUAL`=上游审批人在 PASS 时以 `routeTargetIds` **多选**要执行的分支列，仅勾选列并行执行（未勾选列不建任务，汇合按 PENDING 判定天然跳过）。
- 并行分支列无需 `label`，直接以节点 `name` 作为下拉选项名；其余契约（旧数据兼容、发布校验口径）与人工路由一致。

**设计器删除交互（2026-10-19）**：分支容器已达最小规模（≤2 列）时点击列头「删除」——自动路由（`AUTO`）维持"删该列并解散整个容器（剩余列子流程提升主干）"；**人工路由（`MANUAL`）不解散容器、不删任何分支列，仅清空被点列内的审批节点子链**（`BranchDeleteAction` 新增 `CLEAR`，列与选项 `label`/`name` 保留，可重新添加审批节点）。原因：发布校验要求 MANUAL ≥2 分支列，解散会把另一列已配置的选项与审批人一并摧毁；前端 `stores/workflow.ts`（`resolveBranchDeleteAction`/`deleteBranch`）与确认文案、列头删除按钮提示（"删除分支内审批节点"）同步区分。

**空分支列的指定审批人回退（2026-10-19）**：PASS 携带 `routeAssignees` 指定审批人时的目标定位由"仅分支列内首个审批节点"扩展为 `routeAssigneeTarget(column, container)`——列内无审批节点（空列或仅直通办理节点，含上述 `CLEAR` 清空后的列）时，**回退为容器后继链上的首个审批节点**，与引擎对空列的流转落点（`advanceFrom(chainNext(容器))`）一致；候选预览（`assigneeOptions`）与引擎登记覆盖共用该口径。定位规则不变：跳过直通办理节点、遇嵌套分支容器即放弃（走向不唯一）。人工并行多个空列回退到同一后继节点时按列顺序首个登记生效（`putIfAbsent`）。详见《工作流提交与审批操作接口设计》§4.6.3。

### 7.5 防重复提交（Redisson 分布式锁）

「保存流程设计」「发布」为**非幂等写操作**，需防重复提交（双击 / 网络重试导致同请求并发到达）：

- **锁维度**：`approval:process:submit:{processId}`（保存与发布共用同一把锁，串行化对同一流程的写操作）
- **获取方式**：`RLock#tryLock(0, 3, TimeUnit.SECONDS)`（`waitTime=0` 不等待立即返回；`leaseTime=3s` 自动释放兜底，防业务异常未 unlock 导致死锁）
- **获取失败** → 抛 `BusinessException(PROCESS_REPEAT_SUBMIT)`（40045）
- **释放**：`finally` 中 `lock.isHeldByCurrentThread() && lock.unlock()`，防误删他人持有的锁
- **Redis 实例**：复用 auth 已引入的 Redis（与 `TokenBlacklistService` 同实例），Boot 2.7 前缀 `spring.redis.*`

```java
// ProcessServiceImpl 示意
RLock lock = redissonClient.getLock("approval:process:submit:" + processId);
if (!lock.tryLock(0, 3, TimeUnit.SECONDS)) {
    throw new BusinessException(ResultCode.PROCESS_REPEAT_SUBMIT);
}
try {
    // 保存设计 / 发布逻辑
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**通用注解 `@RepeatSubmit`（2026-10-19 起全后端写接口统一纳管）**：

上表为 Service 层**业务级互斥锁**（按实体 ID 串行化），另在 `ocr-web` 新增横切防重组件，覆盖**所有 Controller 写方法（纯查询除外）**：

- **组件**：注解 `com.paddleocr.web.annotation.RepeatSubmit`（属性 `prefix` 缺省 `Controller#方法名`、`expireSeconds` 缺省 5）+ 切面 `com.paddleocr.web.aspect.RepeatSubmitAspect`（依赖 `spring-boot-starter-aop`，见 §10）
- **锁 key**：`web:repeat_submit:{前缀}:{userId}:{参数指纹 MD5}`——同一用户 + 同一接口 + 相同参数才互斥，不同参数立即放行；未登录接口（注册/登录/刷新）按 `anonymous` 口径拦截
- **锁语义**：`tryLock(0, expireSeconds)` 不等待，重复请求立即 40045；**方法成功后不主动解锁**（防重窗口完整覆盖 `expireSeconds`，对齐 `createAndSubmit` 手写锁语义）；**失败立即解锁**允许马上重试；`leaseTime` 兼作死锁兜底
- **指纹规则**：`Arrays.deepToString(args)` 后 MD5（DTO 依赖 lombok `toString`）；`ServletRequest/ServletResponse/MultipartFile` 以类名占位不参与指纹
- **与业务锁的关系**：切面织入于 Controller 层，天然在 Service 事务边界之外；与既有业务级锁（流程提交锁 / 实例推进锁 / 单据发起锁 / 用户级建单锁）互补不冲突——注解拦「同用户同参数重复请求」，业务锁拦「跨用户并发的互斥写」
- **覆盖清单（26 个写方法）**：认证 4（register/login/refresh/logout）、机构 3、角色 3、用户管理 4、律所选聘 4、流程配置 6、实例发起/撤销 2、任务办理 1、抄送已阅 1；OCR 识别（结果不落库）与 `next-approvers`/`node-buttons`（dryRun 预览）等纯查询不加

## 8. 安全设计要点

| 主题 | 设计 |
|---|---|
| 垂直越权 | 流程配置域为管理端能力，Controller 全部 `@PreAuthorize("hasRole('ADMIN')")`；非 ADMIN 返回 40300（复用现有 `RestAccessDeniedHandler` / `GlobalExceptionHandler` 双通路） |
| 鉴权 | 复用现有 JWT 过滤器链，无需新增；接口仅需在 `SecurityConfig` 白名单之外（默认已 `/api/**` 需认证） |
| SQL 注入 | 全部 `LambdaQueryWrapper`；`keyword` 模糊查询用 `like` 包装器参数，禁止 `apply`/`last` 拼接 |
| 并发唯一 | 新增撞 `uk_code` 由 `DuplicateKeyException` 映射 40040；版本号生成在 `ProcessService#saveDesign` 内用 `uk_process_version` 兜底 |
| JSON 注入/超大负载 | `design_json` 为服务端校验后存储；DTO 对 `designJson` 做长度上限校验（如 ≤ 512KB），防超大 JSON 拖垮接口 |
| 状态机约束 | 所有写操作先 `selectById` 判断当前状态再执行；状态判断与更新同事务（`@Transactional(rollbackFor = Exception.class)`），防并发下的非法流转 |
| 越权数据 | `processId` 来自路径，Service 统一 `selectById` 校验存在性 + `deleted=0`（逻辑删除自动过滤），不存在返回 40041 |
| 防重复提交 | 保存设计 / 发布接口用 Redisson 分布式锁 `approval:process:submit:{id}` 串行化；`tryLock` 失败返回 40045；`leaseTime=3s` 兜底防死锁 |

### 9.7 发布流程 `POST /api/approval/process/publish/{id}`

请求：路径参数 `id`，无 Body。

服务端动作：校验 `draft_json` 存在 → 对草稿做**发布级完整校验**（§7.4）→ 生成新版本 `v{n+1}`（快照 = 校验通过的草稿内容，落库后不可变）→ `current_version = v{n+1}`、流程状态置 `PUBLISHED`；校验失败返回 `PROCESS_DESIGN_INVALID`。任何状态均可发布，**每次发布都产生一个新版本，同一时刻仅 `current_version` 指向的版本为已发布版本**。

响应 `data`：`string`，本次发布的版本号（如 `v2`）。

失败：`40041` 不存在、`40042` 设计不合法、`40044` 无可发布草稿（`draft_json` 为空）、`40045` 重复提交（分布式锁未获取）。

请求：路径参数 `id`，无 Body。服务端动作：仅 `PUBLISHED` 态 → 置 `DISABLED`。

| updateTime | string | 发布时间 |

失败：`40041` 不存在。

> **前端交互约定（向导页「版本视图」切换器）**：切换器**注入向导第 2 步设计器工具栏右侧扩展位**（`WorkflowToolbar` 具名插槽 `#version`，取代原前端示例「版本号」下拉假数据；独立设计器页不传插槽则不渲染；基本信息步骤不展示）；编辑态以**真实流程 id**（`route.query.id`，不写死）调用本接口获取版本数；选项 =「草稿」（恒为第一项，value 用非空哨兵 `'draft'` 以规避 el-select 空串回显歧义；未发布过时仅此一项）+ 各历史版本（倒序），以**下拉单选框**呈现（无提示文案），最大版本号（`currentVersion` 指向的当前已发布版本）右侧以绿色小字「当前版本」标记，选中历史版本调 §9.6（带 `version`）加载对应快照进画布；**进入编辑页时下拉与画布同步定位：已发布流程默认选中并展示「当前版本」快照，从未发布（第一次）默认选中并展示「草稿」**；**新增/从未发布流程版本列表为空，切换器默认只显示单项「v1」**（当前编辑内容即将发布为 v1）。切换失败不改变当前视图；查看历史快照时的保存/发布针对画布当前内容（即把快照内容存为草稿/发布为新版本）。

### 9.10 删除流程 `DELETE /api/approval/process/delete/{id}`

请求：路径参数 `id`，无 Body。服务端动作：仅 `DRAFT` 态 → 逻辑删除（连带逻辑删除其版本记录）。

响应：`data` 为 `null`。失败：`40041` 不存在、`40043` 非 DRAFT 态。

> 前端当前操作列未暴露删除按钮，本接口为后端预留能力（草稿态清理），是否暴露由前端后续决定。

### 9.11 指定人员/指定角色下拉（复用系统设置接口，前端交互约定）

流程配置页（`/approval/process-config/edit`）的「指定人员 / 指定角色」（第 1 步基本信息发起范围 + 第 2 步节点设置的审批人与发起人只读态）**不再使用前端写死样例数据**，改为调用系统设置域已有接口，**后端搜索逻辑保持不变**：

| 场景 | 接口 | 入参 | 后端匹配 |
|---|---|---|---|
| 指定人员 | `GET /api/users/page` | `username` + `pageNum/pageSize` | 用户名/昵称**前缀**匹配（`likeRight`） |
| 指定角色 | `GET /api/roles/page` | `keyword` + `pageNum/pageSize` | 角色编码/角色名称**前缀**匹配（`likeRight`） |

前端交互约定：

- **单个输入框模糊搜索**：下拉为 `el-select` 的 `multiple + filterable + remote + reserve-keyword + clearable`，输入即查（防抖 300ms，`pageSize=20`）；空关键词取首页，便于直接浏览选择。
- **可多次搜索多次选择**：`reserve-keyword` 保留关键词，选中后不重置输入；已选但不在当前结果里的项由前端名称缓存补回（排在后段），标签不会退化成 id。
- 展示名规则：人员取昵称（缺省用户名），副标题显示用户名；角色显示角色名称，副标题显示角色编码。
- **名称回显**：后端无「按 id 批量查名」接口，前端维护 `id → 展示名` 进程内缓存（搜索命中时写入），并在进入编辑页时**预热首页各 100 条**（`pageSize=100`，后端上限），供已保存流程的画布节点与只读态按 id 回显名称；预热失败允许下次重试，超量未命中时回退显示 id。

## 13. 风险与取舍

| 风险 | 影响 | 应对 |
|---|---|---|
| 流程设计 JSON 服务端不建模 | 无法做节点级强校验 | 本期做最小结构校验（§7.4）；运行时引擎（V2）再引入节点级建模与语义校验 |
| 发起范围存 JSON 文本 | 无法按发起人范围做 DB 级过滤、人员/角色 ID 无引用完整性 | V1 由前端约束 ID 合法性；V2 精确关联时拆 `flow_process_initiator` 关联表 |
| 草稿与发布快照分离存储 | 草稿可随时改、不影响已发布版本 | `draft_json` 仅保存动作覆盖；版本快照发布即冻结、禁止 update（§4.3）；运行态（V2）引用 `current_version` 快照，与草稿隔离 |
| 版本号并发生成冲突 | 撞 `uk_process_version` | 版本号由 `current_version` 单调递增 + 唯一索引兜底；冲突重试或返回系统异常 |
| 状态判断与更新并发 | 非法流转 | 状态机写操作同事务 + 先查后改（`@Transactional`），配合状态枚举收敛 |
| `design_json` 超大负载 | 接口被大 JSON 拖垮 | DTO 长度上限校验（默认 512KB，§10 可配） |
| 雪花 ID 回显精度丢失 | 前端 id 变形 | DO/VO 的 `Long id` 全部 `ToStringSerializer`（§7.1） |
| 管理接口越权 | 数据破坏 | Controller 全部 `@PreAuthorize("hasRole('ADMIN')")`（§8） |
| Redisson 锁依赖 Redis 可用性 | 防重复提交失效 | `tryLock` 在 Redis 不可用时按可重试错误处理（不静默放行写操作）；锁 `leaseTime=3s` + `finally` 释放兜底防死锁 |
| 人员/角色名称回显依赖前端预热缓存 | 超出预热范围（各 100 条）的已选 id 画布上回退显示 id | 后端暂无按 id 批量查名接口（§9.11）；V2 如需精确回显，补 `GET /api/users/names`、`GET /api/roles/names`（按 id 批量）后去掉前端缓存兜底 |

## 14. 子流程节点（SUB_PROCESS）扩展指引（2026-10-22）

新增节点类型 **`SUB_PROCESS`（子流程）**：节点属性**内嵌**完整子设计 `props.subDoc`（结构与 `WorkflowDoc` 一致，root 固定 `START`），设计器点击节点钻入子流程视图继续设计（面包屑导航、支持嵌套 ≤3 层）。完整设计见《工作流子流程节点设计.md》。对配置域的影响：

- **无新增表与接口**：`subDoc` 随父 `design_json` 一起走既有保存草稿/发布快照/版本不可变语义；
- **发布校验（§7.4）递归化**：对 `subDoc` 递归执行全部既有规则 + 深度 ≤`approval.sub-process.max-depth`(3) + 分支容器（CONDITIONS/PARALLEL）分支列内禁止 SUB_PROCESS，错误码 40065~40067，错误信息带「子流程【X】内：」前缀；
- **前端**：`types/workflow.ts` 增 `NodeType.SUB_PROCESS`/`SubProcessProps`；`stores/workflow.ts` 增设计视图栈；`useWorkflowValidate` 递归校验 subDoc。
