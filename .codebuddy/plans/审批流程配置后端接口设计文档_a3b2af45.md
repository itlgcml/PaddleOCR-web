## 用户需求
根据前端 `/approval/process-config`（流程配置列表页）和 `/approval/process-config/edit`（两步向导：基本信息 + 流程设计）已实现的交互，设计一份**后端接口设计文档**，生成 Markdown 文件存放到 `backend-docs` 目录，格式参考 `backend-docs/用户注册与登录功能.md`。

## 产品概述
产出物为一份「审批流程配置接口设计」后端设计文档（仅文档，不写 Java/前端代码），内容覆盖流程定义的数据模型、状态机、版本策略、接口清单、错误码、分层落地与安全设计，作为后续后端开发的依据。

## 核心内容
1. 数据模型设计：`flow_process`（流程定义）+ `flow_process_version`（流程版本）两张表，含 DDL 与字段取舍说明。
2. 状态机与版本策略：流程状态 `DRAFT → PUBLISHED → DISABLED`（停用后可再发布）；保存草稿/发布时递增生成版本（v1/v2/v3），支持按版本查询历史流程设计 JSON。
3. API 设计：流程配置分页列表、新增（基本信息）、更新基本信息、详情、保存流程设计、查询流程设计（含指定版本）、发布、停用、版本列表、删除等接口的完整出入参与 JSON 示例。
4. 错误码设计：在 `ResultCode` 未占用段（40040 起）新增审批流程段错误码。
5. 核心类设计、安全设计（管理端 ADMIN 鉴权）、配置项、测试要点、实施顺序、风险取舍，严格对齐现有后端多模块分层与命名约定。


## 技术栈与工程约定（文档须严格遵守）

- 后端技术栈：JDK 8 + Spring Boot 2.7.18 + MyBatis-Plus 3.5.x + Druid + MySQL（多模块 Maven：`ocr-common` / `ocr-client` / `ocr-dal` / `ocr-service` / `ocr-web`）。
- 统一响应 `com.paddleocr.web.common.ApiResponse<T>`：`{ code, message, data, timestamp }`，`code=0` 成功。
- 错误码 `com.paddleocr.web.common.ResultCode`：0 成功 / 4xxxx 客户端 / 5xxxx 系统 / 503xx OCR；审批流程段取未占用的 **40040 起**（已占用 40020~40034、40100~40103、40300、50000/50001、50301~50303）。
- DO 规范：`@TableName` + `@TableId(type=ASSIGN_ID)` + `@JsonSerialize(ToStringSerializer)`（Long id 序列化为字符串）+ `@TableLogic` + 审计字段 `createTime/updateTime` + 字段级 `@Schema`。
- DTO/VO 位置 `ocr-service/.../model/dto`、`model/vo`；Controller 采用动作后缀风格 `POST /create`、`PUT /update/{id}`、`DELETE /delete/{id}`、`GET /tree`（与现有 `OrgController` 一致），`@PathVariable Long id`。
- 分页 `PageResultVO<T>`：`{ records, total, pageNum, pageSize }`。
- 审批流程域归入 `controller/approval`、`service/approval`，`@Tag(name="审批流程-流程配置")`；管理接口 `@PreAuthorize("hasRole('ADMIN')")`。

## 实现方案（文档核心设计决策）

### 1. 数据模型（两表）
- `flow_process`：`id`、`code`（流程编码，唯一）、`name`、`description`、`initiators`（「谁可以发起」多选，JSON 文本列存储）、`status`（DRAFT/PUBLISHED/DISABLED）、`current_version`（当前版本号）、审计字段、`deleted`。
- `flow_process_version`：`id`、`process_id`、`version`（如 v1）、`design_json`（LONGTEXT，存前端 `WorkflowDoc` 完整 JSON：`{name, updatedAt, root}`）、`status`（草稿/已发布）、审计字段、`deleted`。
- 唯一约束：`flow_process.uk_code(code)`；`flow_process_version.uk_process_version(process_id, version)`。

### 2. 状态机与版本策略
- 状态流转：`DRAFT → PUBLISHED → DISABLED`，停用后可再发布回 `PUBLISHED`；非 `DRAFT` 态禁止修改基本信息与流程设计。
- 发布时服务端校验 `design_json`：根节点类型必须为 `START`、节点名称非空、审批节点已选审批人（对应前端 `useWorkflowValidate` 的服务端等价校验），校验失败返回 `PROCESS_DESIGN_INVALID`。
- 版本递增规则：草稿保存生成 `v{n}`（draft 态可覆盖当前草稿版本或追加新版本），发布时把当前草稿版本标记为已发布并更新 `current_version`。

### 3. API 清单（动作后缀风格，前缀 `/api/approval/process`）
- `GET /page`：流程配置分页列表（支持 `keyword`/`status` 过滤）。
- `GET /detail/{id}`：流程配置详情（含基本信息 + 当前版本号）。
- `POST /create`：新增流程配置（仅基本信息，初始 DRAFT）。
- `PUT /update/{id}`：更新基本信息（仅 DRAFT 态）。
- `PUT /design/{id}`：保存流程设计（写入/更新草稿版本 `design_json`）。
- `GET /design/{id}`：查询流程设计（可选 `version` 参数查历史版本）。
- `POST /publish/{id}`：发布流程（校验 + 状态流转 + 版本落定）。
- `POST /disable/{id}`：停用流程（仅 PUBLISHED 态）。
- `GET /versions/{id}`：版本列表（version + status + 更新时间）。
- `DELETE /delete/{id}`：删除流程（逻辑删除，仅 DRAFT 态，可选）。

### 4. 错误码（40040 起）
`PROCESS_CODE_EXISTS(40040)`、`PROCESS_NOT_FOUND(40041)`、`PROCESS_DESIGN_INVALID(40042)`、`PROCESS_STATUS_ILLEGAL(40043)`、`PROCESS_VERSION_NOT_FOUND(40044)`。

### 5. 文档章节结构（对齐参考文档）
1 现状分析 → 2 目标与范围 → 3 技术选型 → 4 数据模型设计（DDL）→ 5 分层落地 → 6 错误码设计 → 7 核心类设计 → 8 安全设计要点 → 9 API 设计（全接口出入参）→ 10 配置项 → 11 测试要点 → 12 实施顺序 → 13 风险与取舍。
